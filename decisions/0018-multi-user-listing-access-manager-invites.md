# ADR 0018: Multi-User Listing Access — Manager Invites

**Status:** **Amended by `decisions/0070` (2026-10-09):** claiming writes the owner to `listing_access`. Accepted (2026-09-24), builds the other half of a table `decisions/0012` already created and `decisions/0015` already started using. Prompted directly by a question about what happens when two people actively work for the same business.

## Context

`listing_access` (`decisions/0012`) was designed from the start to support more than one person on a listing: `entity_id`, `user_id`, `access_level` ENUM (`owner`, `manager`), `granted_by_user_id` — `owner` with full authority (edit, transfer, invite/remove managers), `manager` with day-to-day authority only. But confirmed by a direct read of `decisions/0015` item 4: the only code path that ever writes to this table is the claim flow itself, and it only ever inserts an `owner` row for the claimant. Nothing anywhere creates a `manager` row. So today, despite the schema explicitly reserving space for it, there is exactly one way for a second real person to act on a listing: share the owner's login — which defeats `session_version`, per-account audit trails, and the entire point of `listing_access` existing as a capability grant rather than a single flag.

This also exposed a real, separate bug while designing the fix: `decisions/0017`'s document-upload endpoint checked `disputes.filed_by_user_id` for who could attach evidence to a dispute, but never checked `listing_access` at all — meaning the claimant a dispute was filed against, or any manager helping them, had no way to upload their own defending evidence. That's corrected in `decisions/0017` directly, cross-referenced here since it's the same underlying gap this ADR closes.

## Decision

**Two new owner-only endpoints, reusing patterns already built rather than inventing new ones:**

- **`POST /listing/api/managers/invite.php`** — gated by `Auth::requireListingAccess($entityId, 'owner')` (the real helper already documented in `architecture.md` §11) so only the current owner can invite, never an existing manager (matching the schema's own "owner has full authority... invite/remove managers" comment). Takes one email address. Reuses `decisions/0015` item 2's exact anti-enumeration pattern: the response never confirms or denies whether the email matched a real account — it always replies "if this is a registered user, they'll receive an invitation." A match creates a `listing_access` row with `access_level = 'manager'`, `granted_by_user_id` = the owner, gated on a confirmation click (same `confirmation_token`/expiry shape as Tier 2 referrals) rather than landing active immediately — the invitee has to actively accept, not just be silently attached to a business. **Deliberately requires the invitee to already be a registered, email-confirmed user** — the same guest-exclusion boundary `decisions/0015` already enforces on filing a dispute; a guest can't be handed real authority over a listing any more than a guest can dispute one.
- **`POST /listing/api/managers/remove.php`** — owner-only, same access check, deletes a specific `manager` row. A manager can also remove themselves (stepping down doesn't need the owner's permission).

**Every action already scoped to "the user owns" broadens to "the user owns or manages" — `decisions/0015` items 3 and 6, updated directly.** Tier 1 self-confirm, Tier 3 vouch-selection, and Tier 4 manual-review intake are all day-to-day verification actions, not ownership-changing ones — a manager legitimately representing the business should be able to do all three. **What stays owner-only, deliberately:** inviting or removing managers (above), transferring the listing, and anything that changes who `entities.owner_user_id`/the `owner`-level `listing_access` row points to. Authority over the business's *existence as claimed* stays with the owner; day-to-day defense and verification work doesn't need to.

**Dispute response, corrected in `decisions/0017` directly:** the document-upload endpoint's access check now includes `listing_access` (owner or manager) on the disputed entity, not just the dispute's filer — so a manager can help the owner respond to a dispute with real evidence, matching the same owns-or-manages principle applied everywhere else in this ADR.

## Consequences

`routes.md` needs two new rows for the invite/remove endpoints. `architecture.md` §11's `listing_access` description gets a note that `manager` rows are now real and written, not just reserved schema.

**Deliberately out of scope, flagged rather than solved:** what happens when an owner leaves the business entirely with managers still active (there's no "promote a manager to owner" transfer flow — that's a real gap, but a different one, closer to `decisions/0015`'s already-flagged ownership-transfer question than to this ADR's narrower "let more than one person act on a listing" scope); what happens when two managers disagree on an edit (no conflict-resolution model exists for simultaneous edits by different `listing_access` holders — first-write-wins by default, same as anywhere else in this codebase without explicit locking); and a cap on how many managers one listing can have (none specified — a first default worth setting if this ever gets abused, not urgent enough to block on now). None of these block shipping the core capability; all are real enough to name rather than silently leave undecided.
