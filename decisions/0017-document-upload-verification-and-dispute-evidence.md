# ADR 0017: Document Upload — Verification & Dispute Evidence

**Status:** **Amended by `decisions/0070` (2026-10-09):** documents are one of the claim routes. Accepted (2026-09-23), builds the document-upload capability `decisions/0015` explicitly deferred — its own words were that it "needs its own secure-storage design (outside the webroot, access-controlled) that's better done once Phase 7's reviewing side exists to consume it." `decisions/0016` is that reviewing side, and it's real now, so the precondition 0015 named for building this is actually met. Per direction: a real upload, not another manual email-to-a-monitored-address workaround. **Revised 2026-09-24, per direction:** adds a hard retention window (auto-purge 72 hours after the related case resolves — resolving this ADR's own originally-flagged open question), server-side image compression on upload, and an automated pre-screening pass that gives the uploader an immediate, explained preliminary verdict — without that verdict ever silently deciding the outcome itself. See the new subsection below. **Revised 2026-09-24 again, per direction: fixed a real access-control bug** — the upload endpoint only let a dispute's filer attach evidence, never the claimant defending against it, backwards from what `decisions/0015` already promises the claimant. Now checks `listing_access` (owner/manager, `decisions/0018`) on both sides. **Revised again same day, per direction:** the OCR pre-screening pass now structures what it reads using `decisions/0011`'s existing Who/What/Where/When/Why classification approach rather than free-text reasoning — reusing an already-established pattern instead of inventing a second one, and picking up that ADR's "classify at intake, store only the classification" discipline as a real privacy benefit here too. See below for how "Who" is adapted for this context without reopening the boundary `decisions/0011` deliberately drew. **Revised a third time same round, per direction and a real hosting constraint you flagged:** the "genuine engineering question" the previous revision left open is now answered, and not in the synchronous design's favor. Bluehost hard-blocks `shell_exec()`/`exec()`/`proc_open()` at the master `php.ini` level — a shared-hosting account can't override `disable_functions` — and even a hypothetical workaround would get killed by Bluehost's resource throttling, since OCR is exactly the kind of CPU/memory-heavy long-running process shared hosting throttles to protect other tenants. So OCR moves off Bluehost entirely, onto an async Railway worker — the real trigger `decisions/0004` said would justify adding Railway, now actually here. This also tightens what "eliminate manual review" can mean: the automated check can now stand in for an admin's own visual inspection of a document when it's genuinely confident, but it was never going to remove the admin's own approve/deny action on the underlying case — that action requires a human's own authenticated request today and continues to. See the rewritten subsection below. **Revised a fourth time, 2026-09-24, per direction: the 72-hour purge cron now explicitly excludes `dmca_notice`-related documents**, which `decisions/0019` keeps permanently for statute-of-limitations reasons rather than on this ADR's normal clock. See the added carve-out below.

## Context

Two real, live intake points currently ask a user to prove something with paperwork but have nowhere to put it:

- **Tier 4 manual-review intake** (`decisions/0015` item 6, on `businessportal.php`): submits a short free-text justification plus a contact phone number, and its own confirmation copy tells the claimant to email supporting documents to a monitored admin address "if they have any" — because no upload path exists.
- **Dispute filing** (`decisions/0015` item 5, `POST /api/disputes/file.php`): a filer alleging a claim is fraudulent submits a written reason with no way to attach proof at all — e.g., their own utility bill or business license showing they're the actual, currently-unrecognized owner.

Both funnel into `admin/claims.php` (`decisions/0016`), which already has a `has_document` field on its decision payload — today that's a manual checkbox an admin ticks after receiving something by email, not a record tied to an actual file. Confirmed by a direct search of the live codebase: there is no `$_FILES` handling anywhere, no upload endpoint, and no non-webroot storage directory. This is genuinely greenfield — nothing to reconcile against, only to build cleanly the first time.

## Decision

**One small, purpose-built upload path, not a general media/file manager:**

- **New table `verification_documents`** — `id`, `related_type` ENUM (`verification_attempt`, `dispute`), `related_id`, `entity_id` (denormalized at write time so hub-scoped admin queries don't need a second join through two different parent tables), `uploaded_by_user_id`, `storage_path`, `original_filename`, `mime_type`, `file_size_bytes`, `uploaded_at`. Denormalizing `entity_id` in matches this codebase's existing comfort with light denormalization for query simplicity (`composite_hash` on `entities` is the same instinct applied elsewhere).
- **`POST /api/documents/upload.php`** — global, not under `listing/api/`, matching the same folder convention `decisions/0015` used for dispute filing. Accepts `related_type`, `related_id`, and one file. Before accepting anything, it re-derives who's allowed to attach evidence to the related row server-side. **Corrected 2026-09-24, a real bug caught while answering a direct question about multi-user listings:** the original version of this check only let a dispute's *filer* (`disputes.filed_by_user_id`) upload — meaning the claimant the dispute was filed against had no way to upload their own defending evidence at all, directly contradicting `decisions/0015`'s own promise that a claimant can "submit supporting evidence" to respond. Fixed: for a `verification_attempt` row, the calling user must either be the claimant who created it or hold `listing_access` (owner or manager, `decisions/0018`) on its entity; for a `dispute` row, the calling user must be either `disputes.filed_by_user_id` (the filer, proving their allegation) or hold `listing_access` (owner or manager) on the disputed entity (the claimant or a manager, defending it) — both sides of a dispute can now submit evidence, which is what the process actually needs. PDF/JPG/PNG only, a 10MB cap (first default, not researched against real file sizes) — anything else is rejected outright, never silently re-encoded or reinterpreted.
- **Storage lives outside the webroot**, exactly as `decisions/0015` said it would need to: `/storage/verification-documents/{entity_id}/{uuid}.{ext}`, filename randomized so a guessed or leaked ID never resolves to a real path. Nothing under this directory is ever served by a direct, public URL.
- **`admin/api/documents/view.php?id=`** is the only way a document is ever read back. It resolves the document's `entity_id` to a hub the same way `decisions/0016` already does for the queue itself, then calls the identical `Auth::requireHubAdmin()` / `requireSuperAdmin()` check every other action in that ADR uses, before streaming the file with its real `mime_type`. A regional admin can view documents only for listings in their own hub — the same boundary as everything else in the claims queue, no separate rule invented for this.
- **`admin/claims.php` gains a document indicator** on any row that has one, linking straight to the gated view endpoint. `has_document` on the decide payload (`decisions/0016`) stops being purely a manual tick: it's now pre-filled from whether a real `verification_documents` row exists for that `related_id`. The manual checkbox stays as a fallback, not removed — for the rare case a document still arrives by email (a file over the size cap, or a claimant who can't get the upload to work) — so the email-to-a-monitored-address path from `decisions/0015` is no longer the *only* option, just no longer the default one.
- **Notification, reusing real infrastructure, no new integration:** on a successful upload, `Mailer.php` emails every admin whose `admin_access` row matches the entity's hub (or holds `super_admin`) — the exact same hub-resolution chain `decisions/0016` already uses to scope the queue — with a direct link into `admin/claims.php`. This replaces the "monitored admin address" idea from `decisions/0015` with something more precise: the actual admins responsible for that hub get told directly, rather than a shared inbox someone has to remember to check and manually route into the queue.

**Deliberately out of scope:** this is not a general document or media manager. It's two intake points, one storage table, one gated viewer — scoped tightly to verification and dispute evidence. Listing photos, or any broader upload feature, is a separate concern with its own design if and when it becomes real.

### Retention, compression, and automated screening — added 2026-09-24, per direction

**Retention — resolves the open question from this ADR's own original Consequences.** A `verification_documents` row, and the file it points to, is purged 72 hours after the case it's attached to resolves: `verification_attempts.status` leaving `pending` (approved or rejected), or `disputes.status` leaving `open` (`claimant_reverified`, `claim_revoked`, `claim_abandoned` — added 2026-09-24, `decisions/0015` — or `resolved`). A short daily cron job — no new infrastructure, the same low-tech scheduling posture this platform already uses elsewhere — finds documents whose parent row resolved more than 72 hours ago and deletes both the database row and the file on disk. A document attached to a still-open case is never purged, however old it gets; the clock starts at resolution, not at upload. This closes the gap this ADR originally flagged rather than resolved: a home address or account number on a submitted document no longer sits on disk indefinitely.

**Carve-out added 2026-09-24, per direction: `related_type = 'dmca_notice'` documents are excluded from this purge cron entirely.** The 72-hour window above is the right default for verification/dispute evidence, but it is the wrong default for a document supporting a DMCA notice (`decisions/0019`) — those are legal records with real statute-of-limitations exposure, and per direction they're kept permanently rather than purged on any clock. The cron's query gains a `related_type != 'dmca_notice'` condition (or equivalently, an early skip) so it never even considers these rows for deletion, rather than relying on a `dmca_notice` row simply never reaching a "resolved" state that would trigger it — an explicit exclusion is safer than an implicit one, since `dmca_notices.status` does reach terminal-looking values (`restored`, `invalid`) that could otherwise be mistaken for a purge trigger by anyone extending this cron later. See `decisions/0019`'s Consequences for the retention reasoning (the 3-year copyright statute of limitations under 17 U.S.C. § 507(b), and why permanent retention is the simplest correct rule once records need to survive an unpredictable future legal challenge).

**Compression — images stay on Bluehost, PDFs move to the same Railway worker OCR needs.** On upload, an image (JPG/PNG) is resized to a sane maximum dimension and re-encoded through PHP's built-in GD library — a compiled extension, not a spawned process, so it's unaffected by Bluehost's `disable_functions` block and cheap enough to run inline on the web request. This has a real side benefit beyond storage size: GD's re-encode strips EXIF metadata as a matter of course, which on a phone-camera photo of a utility bill can otherwise carry GPS coordinates and other metadata well past what's needed to prove ownership — a second, independent privacy win, for free. **PDF compression answers the "Pdf php resize?" question directly: not on Bluehost, but yes, on the worker.** Meaningfully shrinking a PDF (recompressing its embedded images) needs Ghostscript or Imagick's PDF delegate, both external-binary territory — exactly what's blocked on Bluehost. Since a Railway worker now exists anyway for OCR (below), it does PDF compression too while it's already holding the file: one async job, two jobs' worth of value, no separate infrastructure decision needed for this alone.

**Automated pre-screening — now necessarily asynchronous, and split by risk, per direction to eliminate manual review wherever the automation can genuinely stand in for it.**

**Why this isn't a Bluehost/PHP-inline design anymore.** Two real constraints you raised rule that out entirely, not just make it awkward: `disable_functions` in Bluehost's master `php.ini` hard-blocks `shell_exec()`/`exec()`/`proc_open()` account-wide — there's no per-account override — so a shared-hosting PHP process can never spawn a Tesseract binary at all, wrapper or not. And even setting that aside, OCR is genuinely CPU/memory-heavy, exactly the kind of long-running binary process Bluehost's resource throttling exists to kill, to protect other tenants on the same box. Both facts point the same direction: this has to run somewhere else. It moves to an async Railway worker — the real, concrete need `decisions/0004` said would justify adding Railway (that ADR names the scraper-to-article pipeline as the original trigger; this is a second, independent one arriving first).

- **Intake validity (hard, deterministic, synchronous, still on Bluehost — blocks nothing legitimate).** Unchanged from before: beyond the existing type/size checks, the file must actually be a readable image or PDF — not corrupted, not zero-byte, not a decoy. Fails closed at upload time, before a `verification_documents` row is even created, with an immediate, specific reason to the uploader ("the file couldn't be read — try a different format or a fresh scan"). Cheap enough to stay inline; nothing here needs the worker.
- **Content relevance (soft — but now genuinely decisive for the *document*, never for the *case*) — structured with `decisions/0011`'s existing Who/What/Where/When/Why approach.** Once a file clears the check above, it's queued for the Railway worker rather than scanned inline: the upload response confirms receipt only, not a verdict — the verdict isn't known yet. The worker fetches the file's bytes from Bluehost through a small, shared-secret-authenticated internal endpoint (not public, never a generally-reachable URL), runs Tesseract OCR against it, and — exactly like `decisions/0011`'s "classify at intake, store only the classification" rule — writes back only a small structured classification, never the raw OCR'd text. The five keys, adapted for this context:
  - **What** — the kind of document detected (utility bill, business license, tax document, unclear).
  - **Where** — an address string found in the document, checked against the entity's own address.
  - **When** — a date found on the document, if any (relevant for judging how current a utility bill is).
  - **Why** — the stated match reasoning shown to the uploader and admin ("business name and address both matched," "no address found matching this listing").
  - **Who — deliberately adapted, not reused as-is.** `decisions/0011` redefines "Who" to mean audience/impact and explicitly walls it off from ever meaning identity, because that ADR's corpus deals in *system-user* identity, governed separately under `decisions/0010`. This document-screening context never touches user identity — the identity question here is *business* identity, already a public, searchable graph-mirror node elsewhere on this platform. So "Who" here means the business/entity the document is claimed to support (matched against `entity_id`/name) — a different, already-public kind of identity than the one `decisions/0011` was protecting, not a reopening of that boundary.

  **A new `review_status` field on `verification_documents`** (`pending` / `auto_confirmed` / `needs_review`) is what actually eliminates manual review, and only for the specific thing that's safe to automate. `auto_confirmed` requires a real, conservative bar: a recognized document type *and* a clear text match on the entity's name or address — not just "OCR ran without error." Anything short of that — no match found, an unrecognized document type, unreadable extracted text, or the worker itself failing or timing out — lands in `needs_review`, the same conservative-by-default posture as everything else in this document set. **What `auto_confirmed` actually changes, precisely:** an admin no longer has to personally open and read a document that the automated check already confidently matched to the listing before acting on the underlying Tier 4 or dispute row — the classification stands in for that one specific manual-inspection step (the raw file is still one click away if they want it anyway). **What it never changes:** the actual case decision. `decisions/0016`'s decide endpoint has always required an authenticated hub-admin's own request — there is no path today, and none is added here, where a Tier 4 intake or a dispute resolves without a human's own Approve/Override/Request-more-info/Deny action landing on it. So "eliminating manual review" here means eliminating the redundant step of an admin re-verifying something the system already confidently confirmed, never eliminating the admin's actual authority over the outcome — which is exactly the same HITL boundary `decisions/0005` already draws for every other automated content decision on this platform, not a new exception carved out for this one. The admin's real options stay: **Accept** (agree with an `auto_confirmed` read, or a `needs_review` one after looking), **Override** (accept a document flagged `needs_review` after inspecting it, or reject one marked `auto_confirmed` — human judgment beats the heuristic either direction, always available), **Request more info** (ask for a clearer or different document without denying the underlying request), or **Deny** (reject the document specifically; the claimant can still pursue another verification tier or resubmit).

**What this leaves open, flagged rather than guessed at:** the worker-to-Bluehost file-fetch endpoint is a new piece of attack surface (shared-secret or signed-request auth, never a public path) that didn't exist before this ADR and needs the same care as everything else that reads these files; and the uploader-facing timing changes now that scanning is async — "how long until I know" depends on Railway worker throughput, not a fixed number yet, so the UI needs a "your document is being reviewed" state rather than an instant verdict, with the actual result surfacing on `businessportal.php` or by a follow-up notification (which one is a smaller build detail, not decided here).

## Consequences

This is the platform's first real file-upload and non-webroot file-storage feature — worth flagging plainly that it needs actual disk-space planning and a place in whatever backup process the hosting setup already runs, small as the expected volume is (verification documents, not user media at any scale), and smaller still now that images are compressed on the way in and everything is purged 72 hours after resolution.

**The privacy consideration this ADR originally only flagged is now resolved, 2026-09-24, per direction:** a utility bill or business license routinely carries a home address, an account number, or other personal detail well beyond what's needed to prove business ownership — but it no longer sits on disk indefinitely. See the Retention subsection above for the mechanism; this document is still never processed by anything in `decisions/0011`'s AI-corpus pipeline (OCR here is a disposable read for a match check, not a step that feeds the shared corpus) — true whether the read happens on Bluehost or, as revised, on the Railway worker.

**This ADR now genuinely depends on `decisions/0004`'s Railway phase, not just references it.** Item 2 of that ADR ties adding Railway to the async queue/worker layer "actually being built" — this feature is what actually builds it, arriving ahead of the scraper-to-article pipeline that ADR originally named as the trigger. `decisions/0004` is updated with a short cross-reference so it isn't read as still purely hypothetical.

The 10MB size cap and PDF/JPG/PNG allowlist are first defaults, easy to revisit later — not researched against what claimants are actually likely to submit. The OCR-based content-relevance check is a heuristic, not a verified-accurate system — its real false-positive/false-negative rate is unknown until it's actually run against real submitted documents, which is exactly why it stays advisory rather than load-bearing.

**Reusing `decisions/0011`'s classification approach here is a real privacy win beyond what that ADR was originally written for.** That ADR's "classify at intake, store only the classification" rule was designed for the AI corpus, not document review — applying it here means the raw OCR'd text of a claimant's utility bill (which can carry far more than a name and address — account numbers, other household members, unrelated line items) is never written to a log or a database row at all, only the five-key classification is. This is a stronger guarantee than the retention window above, not a replacement for it: retention limits how long the file itself and its classification exist; this limits what ever gets captured from the file's contents in the first place.

`decisions/0015` item 6 and `decisions/0016` item 2 (the Tier 4 approve action) are both updated to point here instead of describing document upload as future, unbuilt work. `architecture.md` §9 and `routes.md` are updated with the two new endpoints and the storage note.
