# ADR 0024: Automated Keyword-to-Category Classification for Crawler Ingestion

**Status:** Accepted (2026-09-24) — the mechanism below; the exact confidence thresholds (80%/50%) are first defaults, not tuned numbers, same status as every other unvalidated threshold already in this document set (the 10MB upload cap, the 3-strike DMCA repeat-infringer count).

## Context

`architecture.md` §18 already says the original 4,376-business category migration "came from keyword rules, not human review" — so this isn't a new idea for the platform, it's an unspecified one. Building `decisions/0023`'s Personal Care & Beauty group against the real radius export minutes ago demonstrated exactly why that matters: a naive substring keyword search ("does the text contain 'spa'?") pulled in real false positives — `Hot Tubs & Spas` (a pool-equipment dealer), `Newspaper Distributors`/`Newspapers` (matched only because "newspaper" contains "spa"), and `Nurses-Licensed-Anesthetist` (matched only because "anesthetist" contains "esthet"). Per direction, a more rigorous version of the same idea — weighted dictionaries, real tokenization, and confidence-gated fallback — closes exactly that gap, and does it for the *ongoing* crawler pipeline, not just the one-time historical cleanup `decisions/0023` already covers for the existing 121 "Other" records.

**This is also the third time this document set has independently arrived at the same shape of solution, worth naming rather than treating as three unrelated designs:** `decisions/0011`'s AI-corpus topic classification, `decisions/0017`'s document Five-Ws screening (`auto_confirmed`/`needs_review`), and now category classification all follow the same pattern — classify with a confidence signal, act automatically above a bar, route to a human below it. Naming this explicitly as a standing platform convention means the next instance of "classify incoming text into buckets" doesn't have to reinvent the shape again.

## Decision

### 1. Weighted keyword dictionaries per category node, replacing whatever unspecified rule produced the original migration
Each Level-1 (and eventually Level-2 leaf) category gets an explicit, versioned keyword list rather than a single implicit check — e.g. Personal Care & Beauty: `barber, salon, haircut, stylist, spa, nails, cosmetology, grooming`; Business & Professional Services: `consulting, accounting, legal, tax, notary, management, staffing`. Incoming business name, description, and metadata tags are scored against every dictionary; a business accumulates a confidence score per category rather than stopping at the first match, so a business matching multiple weak signals in one category and nothing in another gets a real, comparative answer instead of a first-hit guess.

**Target list, as of 2026-09-24:** these dictionaries are built against `decisions/0028`'s Refined 24-Group Level-1 Master Taxonomy — the real, enumerated group list this ADR originally didn't have (see Consequences below, as originally written). Groups 1–23 are the classifier's primary targets — real, bounded industries a keyword/dictionary match can meaningfully confirm. Group 24, "Local & Community Services," is a strict fallback for businesses that genuinely span multiple category boundaries or serve a uniquely local/niche function — not a generic catch-all — so it should not simply absorb every low-confidence result; a low-confidence score routes to admin review (§3 below) exactly as any other category would, not automatically into group 24.

**Group 24 is never an auto-assign destination, independent of confidence (2026-09-24, matching `decisions/0023` §2a's bulk-pass rule).** Groups 1–23 alone are eligible for the >80% auto-assign path in §3 below. If the highest-scoring category for an entity is group 24, that result routes to the admin review queue regardless of its confidence score — a high-confidence dictionary match against a "spans multiple boundaries" fallback isn't the same kind of evidence a high-confidence match against a real named industry is, and only a human reviewing the record can actually confirm a genuine multi-boundary/niche fit. This closes the same gap for ongoing intake that `decisions/0023` §2a closes for the one-time 121-record pass, so the two mechanisms stay consistent rather than diverging on this point.

### 2. Real tokenization, not substring matching — the direct fix for today's false-positive failure mode
**Word-boundary matching, not substring containment, is the specific, concrete fix for what actually went wrong when this was done by hand today.** "Spa" must match the token `spa`, never appear-inside `newspaper`; "esthet" must match a real token stem, never appear inside `anesthetist`. On top of that: stemming/lemmatization (`styling`/`styled`/`stylist` all reduce to the same root) so the dictionary doesn't need to enumerate every inflection by hand, and stop-word filtering (`and`, `the`, `at`, `in`) so scoring isn't diluted by filler text. **Confirmed: none of this needs an external binary or heavy processing** — word-boundary regex, a stemmer (e.g. a Porter-stemmer implementation), and a stop-word array are all plain PHP, unlike `decisions/0017`'s OCR case. This runs inline, synchronously, during ingestion on Bluehost itself; it does not hit the `disable_functions`/resource-throttling wall that pushed OCR to the Railway worker, and doesn't need to.

### 3. Confidence thresholds — a smarter pre-fill inside the existing mandatory review, not an exception to it
**High confidence (>80%), category among groups 1–23: the category is set automatically.** **Low/ambiguous confidence (<50%), or a highest-scoring category of group 24 at any confidence (see §1 above): no category guess is written; the entity routes to the admin review queue instead.** This has to be stated precisely against `decisions/0005`, which is absolute ("no automated or AI-generated output enters the permanent graph without an explicit manual admin sign-off... regardless of how confident the AI system is"): **for a brand-new crawler-ingested entity, that staging-and-sign-off requirement doesn't change here.** A high-confidence category assignment means the field the reviewing admin sees is already correctly filled in — it does not mean the entity skips the human review `decisions/0005` requires before anything goes live. This is the same relationship `decisions/0017` already established between `auto_confirmed` documents and the admin's still-mandatory case decision: automation removes redundant manual effort on something already confidently determined, never the human's actual sign-off. Low-confidence entities route into `admin/listings.php` (`decisions/0022`, sequenced 2.6.1) exactly as they would anyway, just pre-flagged as needing a category decision specifically rather than a blank field.

### 4. Two different jobs this classifier does, worth keeping distinct
- **Going forward:** every future crawler-ingested entity gets scored at intake, feeding the category field an admin sees during the mandatory `decisions/0005` review — this is the ongoing mechanism that prevents a second "121 businesses in Other" backlog from accumulating.
- **Against the existing 4,376 already-live businesses:** re-running this classifier is a data-*correction* operation on already-published metadata, not new content clearing initial review — no `decisions/0005` staging gate applies, since these records are already public. High-confidence corrections can be applied directly; recommended (not yet decided) is a simple audit trail (old category → new category, timestamp, "reclassified by automated pass") rather than a full per-record human approval flow, since this is bulk metadata cleanup, not a trust or visibility decision. `decisions/0023`'s one-time manual pass for the current 121 stays the right near-term move for that specific, already-known, small batch — this classifier is the mechanism that keeps the *next* 121 from ever accumulating, not a replacement for the cleanup already scoped there.

## Consequences

`architecture.md` §18 gets this classification mechanism documented alongside the taxonomy it feeds. `decisions/0022`'s `admin/listings.php` (2.6.1) — already sequenced first among the remaining admin sub-tools specifically because it's the crawler pipeline's completion half — is where a low-confidence entity actually lands; this ADR is the logic that decides whether an entity reaches that queue with a filled-in category or an empty one. `decisions/0023` §2a (amended 2026-09-24) now runs this classifier, not a manual pass, for the existing 121; this ADR is what keeps that from being a recurring cleanup either way. The keyword dictionaries themselves (which words, what weights) are a content/tuning task for whoever owns the category list day-to-day, not fixed by this ADR — same posture as `decisions/0017` leaving its OCR match bar "conservative, revisit once real data exists." **Update, 2026-09-24:** the real 24-group target list this ADR's dictionaries classify into is now `decisions/0028`'s Refined 24-Group Level-1 Master Taxonomy — see §1 above.
