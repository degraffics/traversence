# ADR 0037: Delegated Custom Roles Beyond Owner/Manager — Configurable Permissions, One Owner-Designated Executive Exception

**Status:** Accepted (2026-09-25) — authority model corrected same day from an initial "owner or manager" framing.

## Context

`decisions/0018` established `listing_access`'s two real levels — owner (full authority) and manager (day-to-day authority) — with inviting/removing a manager kept owner-only. `decisions/0036` restricted Location Group linking to owner-level authority, with one narrow exception (below). Per direction, the platform also needs roles below manager — staff who handle a slice of a listing's work (responding to notifications, managing inventory, working quotes) without full manager authority — and a named role isn't enough on its own: there has to be a real way to configure what that role can actually do.

## Decision

**Structural authority — creating a Location Group (`decisions/0036`) or creating further delegated roles — belongs to the owner alone, with exactly one narrow exception, per direction 2026-09-25 (corrected from an earlier "owner or manager" framing).** The owner may designate exactly one manager as **Executive**, explicitly authorizing that one person to also link listings and create further delegated roles. This is a deliberate, owner-granted elevation — never automatic to every manager, never self-assigned, and never granted by anyone other than the owner. **No further delegation past this one level:** an Executive-level manager cannot designate another Executive, and cannot pass linking or role-creation authority to anyone else — the chain stops at owner → one Executive, never a cascading hierarchy. Every other manager, and every role created below manager, has neither capability regardless of how it's configured.

**Creating a delegated role (below manager) is a configuration action, per direction — not a fixed label pick.** When the owner (or the one Executive, if designated) creates a role below manager, they configure what that role can actually do — which parts of the listing's day-to-day work (responding to notifications, viewing or managing inventory, working Quotes, and so on) it has access to — rather than the platform offering a small set of hardcoded named roles with baked-in behavior. This is the same "settings, not a fixed menu" instinct already applied elsewhere on this platform (e.g., `decisions/0032`'s self-defined sales process/SLA, left to the business rather than platform-dictated) — a listing's owner knows what a given helper actually needs access to better than a generic role name could capture.

**Inviting a new manager stays owner-only, unaffected by this ADR (`decisions/0018`).** Designating a manager as Executive is a separate, additional owner action on top of an existing manager grant — it doesn't change who can become a manager in the first place, only whether one particular existing manager also carries structural authority.

## Consequences

This extends `listing_access` beyond its current owner/manager ENUM (`decisions/0002`, `decisions/0018`) into a real permissions model — needing its own schema (an `is_executive`-style flag or equivalent, capped at one per listing, plus a structure capable of representing a configurable set of capabilities for roles below manager) and its own settings UI for the owner (or the Executive) to configure a role at creation and edit it later. Neither is designed yet, nor is the enforcement mechanism that actually caps Executive designation at one per listing. The actual list of configurable capabilities for roles below manager (notification visibility, inventory edit rights, Quote handling, and whatever else comes up) is deliberately left open here rather than speculatively enumerated — the same posture `decisions/0018` already took toward its own unresolved gaps (a manager cap, promote-to-owner transfer): name it, don't guess at it before a real case demands the specifics. `decisions/0036`'s linking-authority language points here for the full reasoning rather than duplicating it.
