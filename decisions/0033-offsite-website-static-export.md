# ADR 0033: Offsite Website Deployment — Static Export/Redeploy Model, Not a Live Public API

**Status:** Accepted (2026-09-25)

## Context

Discussion of the Website Builder module raised three possible ways a client could get a dedicated website: (1) Traversence hosts a landing page for them directly — already effectively promised as Cornerstone's "Primary Digital Presence & Gateway Architecture" deliverable in `commercial.md` §2; (2) a live, public API a client's own external site polls for data; or (3) a generated, deployable site package the client hosts on their own server, with Traversence remaining the sole admin backend. Per direction, this ADR settles on the third as the actual mechanism, distinct from (1) and (2).

## Decision

**Traversence remains the sole, authoritative write path.** A client inputs and manages inventory, content, and communications through Traversence's own admin/listing-management dashboard — never a second, independently-editable copy of that data. This is the same single-source-of-truth discipline `composite_hash` already protects on the ingestion side (never let two sources both think they're authoritative over the same record), applied here to outbound deployment instead of inbound scraping.

**Deployment is a generated export, not a live connection.** On a trigger (see below), Traversence packages that listing's current inventory/content state into a self-contained, deployable bundle — the "zip" — which the client uploads to whatever hosting they choose, on their own domain. The resulting site has no live runtime dependency on Traversence's servers to render its pages.

**Sync cadence: both manual and automatic, client's choice, per direction.** A manual "Redeploy" action the client triggers when ready, and an automatic sync mode that regenerates and redeploys on its own, are both supported — not a single forced mode. Different clients have different comfort levels with unreviewed changes going live automatically; this isn't a case where one mode is simply correct.

**The offsite site still writes back to Traversence, per direction — "the offsite location flows back to its home."** If the listing portal is where this business actually conducts business, an inquiry or Quote request submitted on the offsite site is real business activity for that listing, not a separate concern — it has to reach the same Communications Center and Quote workflow (`decisions/0032`) that the on-platform listing uses, not a parallel or disconnected one. This is a single lightweight write-back endpoint, not a full public API surface — a much smaller, safer thing to secure and support. It carries the same app-scoped/contextual-identifier rule `prd.md` Tier 3 already sets for third-party integrations: never the raw internal `entity_id`/`actor_user_id`. Submissions through it are subject to the exact same dual-accounting and HITL rules (`decisions/0002`, `decisions/0005`) as any other write — the offsite front door gets no attribution or safety exemption for being hosted elsewhere.

**Real SEO value for the client, per direction, clarified — the traffic flows into the client's own site, not just out of it.** The value proposition isn't only that a dedicated external site can accrue its own traffic and backlinks in the abstract — it's that Traversence's own Directory/Discovery listing page for that business, the business's own Facebook presence, and Google's own organic indexing all point real, authoritative inbound traffic and backlinks *at* the client's independently-hosted site once it exists as its own real, crawlable domain. A page living only inside Traversence's own domain can't accumulate that same independent domain authority for the client; a real external site the client owns can. This isn't a new mechanic to invent — it's the existing Conversion Engine (`commercial.md` §0's "Direct-to-Operator Commerce": traffic routes straight to the partner's own ecosystem, no centralized middleman) doing exactly what it already promises, concretely, for a client using this specific deployment model. **Concrete requirement this implies:** the Directory/Discovery listing template needs a real, followed (not `nofollow`, not JS-hidden) outbound link to the client's external site when one exists via this model — the link itself is the mechanism that makes the Conversion Engine's promise actually deliver SEO value, not just traffic.

**Confirmed, per direction (2026-09-25): the generated site also includes a "Powered by Traversence" attribution and backlink, pointing the other way.** Same pattern site builders like Wix, WordPress.com, or Mailchimp already use — visible attribution by default that doubles as real backlink value to the platform, complementary to (not a replacement for) the client-facing benefit above. **Removal, confirmed per direction (2026-09-25): removable upon request, Cornerstone tier only.** Core and Strategic sites keep the attribution/backlink regardless; a Cornerstone partner can have it removed on request — not automatic, and not available below Cornerstone. Still open, and not decided by this confirmation: exactly where/how the attribution renders on the generated page.

## Consequences

This is explicitly distinct from hosted API access (a separate, developer-facing Tier 3 concept for a business's own external systems pulling live data) and from Traversence directly hosting the client's site (Cornerstone's existing promise, which this ADR doesn't replace — a client who wants Traversence to just host it can still have that; this ADR is for the client who wants their own hosting instead). `prd.md` gains a new, concretely-shaped Tier 3 entry for this export/redeploy mechanism. `commercial.md` should eventually clarify how this relates to Cornerstone's "Primary Digital Presence" deliverable — whether this is an alternate delivery mode of the same promise, a distinct add-on, or reserved for a specific tier — which is not resolved here and needs its own pricing/scoping pass.
