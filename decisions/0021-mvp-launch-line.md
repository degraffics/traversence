# ADR 0021: The MVP Launch Line — Core Value, Post-Launch Deferral, and the "No Split Loops" Rule

**Status:** Accepted (2026-09-24) — both open items below are now answered directly, per Jason: the pilot region's listings were seeded via direct SQL, not the live crawler pipeline (§3, resolved, no guardrail violation), and the launch trigger is readiness-based rather than a fixed calendar date (§4, recorded as stated rather than forced into the generic framework's assumption).

## Context

`prd.md`'s first draft flagged this as a real, unresolved gap: "Tier 1/2/3 tracks build sequence, not necessarily what counts as 'MVP launch.' Worth stating explicitly if it differs." `decisions/0020` (Tier 2 dependency sequencing) deliberately didn't answer it either — it said plainly that build order and launch scope are different questions, one technical, one a business call. Per direction, the fix has three parts: defining core value (the bare-minimum features a user needs for the product's primary goal), moving secondary items to a post-launch roadmap, and tying the boundary to a hard launch date to force real discipline rather than letting scope creep indefinitely.

**The sharper piece, and the actual reason this ADR exists now rather than staying a generic exercise:** applying that framework to `decisions/0020`'s reconciliation of the claim entry point and the admin Claims queue (both moved into Tier 1 together, since they'd shipped together) surfaced something the three-part framework alone doesn't say explicitly — **"defining core value" isn't just picking which individual features matter most, it's making sure the launch line never cuts through the middle of a two-sided loop.** A user-facing intake with no way to act on what it collects (or the reverse — a review mechanism with nothing feeding it) isn't half a feature at half the value; it's close to zero value, and in the claim/dispute case, actively worse than not shipping either half, since it invites real user action into a process that can't complete. This is worth naming as its own rule, not folded silently into "core value," because it changes how the line gets drawn: not by ranking features individually, but by finding every loop crossing the candidate line and checking both halves land on the same side.

## Decision

### 1. The "No Split Loops" rule — the actual mechanism for drawing the line, not just a value judgment
A "loop" here means any pairing of a user- or system-facing intake with the action that completes it: a claimant files something and an admin decides it; a scraper stages content and an admin approves it; a search returns a result and a page exists for someone to land on. **The MVP boundary must never separate the two halves of a loop that's otherwise going to be live.** Where a loop is complete, it's evaluated as a whole for in-or-out; where only half a loop can realistically ship by launch, the honest choice is to hold the whole loop for post-launch, not ship the half that collects without the half that resolves.

### 2. Core value, redefined through that rule — the recommended MVP boundary
**IN (launch line):**
- Everything already in Tier 1 as reconciled by `decisions/0020` — directory search, auth, the four verification tiers, claim entry paired with the admin Claims queue, dispute filing paired with its resolution flow, document upload paired with its admin-gated viewer, manager invites, and the DMCA mechanism's code (its *safe-harbor status* is a separate, external question — see the flagged item below, not a code-completeness one).
- **Tier 2.1 (public business detail pages; Hub/Geo-Hub/Micro-Cluster landing pages) — reclassified here from "next tier of build work" to "part of core value," under the No Split Loops rule specifically.** A resident directory that returns search results with nowhere to click through to is the intake half of a loop with no completion half — the same shape of problem as a claim form with no review queue, just less obvious because both halves look like "just content pages" rather than a workflow. `decisions/0020` already sequenced these two first for dependency reasons; this ADR adds a second, independent reason they can't be deferred past launch.

**OUT (post-launch / Phase 2), with one hard coupling condition:**
- Tier 2.2 (Dual-Gateway landing, Chameleon dual-behavioral routing, "Let's Explore" narrative entry, corridor map) — genuinely deferrable; nothing here is one half of an otherwise-shipping loop, it's polish and a second navigation path onto content that already works via direct links and existing `/directory`/`/discovery` routes.
- **Tier 2.3 (editorial article template, AI-generated per-listing articles) — deferrable, but only as a complete unit with its own HITL review counterpart, never split further.** `decisions/0005` requires every piece of AI-generated content clear a human sign-off before publishing. If Tier 2.3 ships before its review mechanism does, that recreates the exact split-loop failure this ADR is naming, at the exact place `decisions/0005` was written specifically to prevent. So the rule for this item isn't just "post-launch" — it's "post-launch, and if it's ever pulled forward, its review gate comes with it in the same release, not after."
- Tier 2.4/2.5 (safety controls, profile feeds, messaging) — deferrable as a block, with `decisions/0020`'s internal order preserved (safety still has to precede the social features it protects, whenever this block does ship).
- Tier 2.6 (remaining admin sub-tools) — deferrable, same reasoning as `decisions/0020`: real urgency scales with how much of the IN list above is live generating things to administer.
- Tier 2.7 (Communities & Groups) — clearly post-launch; no design pass exists yet to even scope it.

### 3. Resolved, per direction: scenario (a) — no guardrail violation, but a real prerequisite now stands before the crawler pipeline can go live for genuinely new ingestion
**Confirmed by Jason: the pilot region's original content/directory listings were seeded directly to the database via SQL — not through the AI/scraper pipeline `decisions/0005` governs.** This is exactly scenario (a) from the flagged question above, not (b): nothing has bypassed the Accepted HITL guardrail, because the live continuous crawler-to-staging-to-review loop has never actually been exercised in production — the current listings simply didn't come through it. `prd.md`'s Tier 1 line item "crawler ingestion" should be read precisely because of this: the *code* exists (bootstrap/API infrastructure), but it has not yet been operated as a live ingestion loop, and the "Scoped, not built" review UI (`admin/listings.php`, `admin/review-queue.php`) was never actually a missing half of something running — both halves are currently dormant, which is consistent (not a split loop) rather than a violation.

**This does create one clean, forward-looking rule, not just a resolved question:** before the crawler pipeline is ever turned on to actually ingest new, real content (a new region's cold-start, or ongoing re-scrapes beyond what SQL-seeded), the admin review-queue side of that loop has to exist first — the same No Split Loops rule from §1, applied prospectively this time instead of retroactively. This is a real gating condition on when autonomous ingestion can start, independent of the general Tier 2.6 sequencing `decisions/0020` gave it for other reasons.

### 4. Hard Launch Date, recorded as stated: a readiness threshold, not a calendar date
**Per direction, this isn't a fixed date at all — the launch trigger is "as soon as we have a working and deployable platform, even basic, it can be shipped," followed by continuous post-launch refinement rather than a big-bang feature-complete release.** This is worth recording precisely rather than forcing it into the generic framework's "hard launch date" assumption: the forcing function here isn't a calendar deadline, it's the MVP Launch Line itself (§2) — the moment the IN list above is genuinely working and deployable, that's the launch signal, with everything in the OUT list explicitly understood as ongoing post-launch iteration rather than a pre-launch backlog to clear first. This still gives the same discipline the three-part framework was after (a real boundary, not indefinite scope creep) without tying it to an arbitrary date that either gets missed or forces a rushed cut.

## Consequences

`prd.md` gains an explicit "MVP Launch Line" marker distinguishing the IN list above from Tier 2.2 onward, resolving the "explicit launch-vs-later line" item its own first draft flagged as missing. This doesn't change `decisions/0020`'s build sequence — the sub-phase order stays the mechanism for *what gets built when*; this ADR answers the separate question of *what has to be true before the public can use any of it*, and when "launch" itself actually happens (a readiness threshold, not a date). The crawler-ingestion prerequisite from §3 (review-queue must exist before the pipeline is ever turned on for real new content) is now a standing gate on that specific future work, independent of this ADR's own IN/OUT list.
