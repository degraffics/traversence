# ADR 0023: Category Taxonomy — Adding "Personal Care & Beauty" and Resolving the "Other" Bucket

**Status:** Proposed — §1 (the new group) is confirmed against real data (Jason shared `85936-Business_list-radius.csv`, a live radius export around Snowflake/Show Low, AZ — 4,479 businesses, 821 raw categories, closely matching the documented 4,376/818 figures). §2/§2a (the old "Other" bucket, now "Local & Community Services" per `decisions/0028`) has its taxonomy-list dependency resolved by `decisions/0028`; it still needs a direct export identifying the 121 live rows before execution — see below.

## Context

`architecture.md` §18 already named both of these as open gaps "worth deciding before launch" when the real, live 23-group/818-leaf category taxonomy was first documented: 121 of the platform's 4,376 migrated businesses sit under a catch-all "Other" group (assigned by keyword rules, never human-reviewed), and there's no "Personal Care & Beauty" group at all today, so barbers and salons currently sit under Professional Services — a real miscategorization, not just an awkward fit. Per direction, both get addressed now rather than staying flagged indefinitely.

## Decision

### 1. Add "Personal Care & Beauty" as a new Level-1 browse group — confirmed against real data, 2026-09-24
A directory that puts a barbershop under "Professional Services" next to accountants and law firms is exactly the kind of miscategorization that erodes the "does this feel like a stiff corporate directory" test `prd.md` holds every feature to. **Checked directly against the real radius export, not the earlier first-draft guess:** 9 real leaf categories, 43 real businesses, genuinely belong here — `Barbers` (3), `Beauty Salons` (25), `Health Spas` (3), `Massage` (1), `Massage Therapists` (1), `Spas-Beauty & Day` (4), `Tanning Salons` (1), `Tattooing` (3), `Cosmetics & Perfumes-Retail` (2). These move into the new group; Professional Services keeps the categories that actually belong there (legal, accounting, consulting, and similar).

**Two things the earlier draft would have gotten wrong, caught only by checking real data:**
- **A naive keyword match ("spa," "esthet," "beauty") pulls in real false positives, excluded here:** `Hot Tubs & Spas` (3, a pool-equipment dealer, not a day spa), `Newspaper Distributors (Whls)` and `Newspapers (Publishers/Mfrs)` (1 and 4 — matched only because "newspaper" contains "spa"), and `Nurses-Licensed-Anesthetist` (5 — matched only because "anesthetist" contains "esthet"). None of these move; they stay exactly where they already sit.
- **Two categories are a real judgment call, resolved here as B2B, not consumer personal-care:** `Beauty Salons-Equipment & Supplies-Mfrs` (1) and `Health & Beauty Aids-Manufacturers` (1) are wholesale/manufacturing businesses that supply the industry, not personal-care service providers themselves — per direction to keep this group about consumer-facing services (matching how barbers/salons were originally framed), these stay in whatever wholesale/manufacturing category already holds them.

`Massage` and `Massage Therapists` appearing as two separate one-off leaf categories is also worth a look during the actual migration — plausibly the same real-world business type recorded under two slightly different raw strings, a taxonomy-consolidation opportunity noticed in passing rather than something this ADR resolves.

### 2. Resolve the "Other" bucket as a one-time manual data pass, not by waiting for the admin taxonomy UI
`architecture.md` §18 already notes the admin taxonomy management UI (view tree with counts, add/rename/reorder/merge leaves, an "Other" review queue) is designed but not built, gated behind the same Phase 7 admin-panel work `decisions/0022` just sequenced. Waiting for that full UI to review 121 records would mean this sits unresolved through several sub-phases of Tier 2.6 for no real reason — 121 is small enough to review directly, out of band, without needing the general-purpose tool built first. **Recommended: a one-time manual review pass (spreadsheet or direct query against the real data), done once, rather than a standing tool built to review a batch this size exactly once.** The permanent "Other" review queue in the admin UI still gets built later per its place in `decisions/0022`'s sequencing — for future crawler-ingested items that land in Other going forward, which is an ongoing need this one-time pass doesn't replace.

**Do the Personal Care & Beauty split first, then the Other-bucket review, not the reverse** — some of the 121 "Other" businesses are plausibly barbers/salons/spas that didn't even keyword-match into Professional Services, meaning they'd otherwise get reviewed once now and then need re-categorizing again the moment the new group exists. Sequencing the group addition first means the Other-bucket review sorts directly into a taxonomy that already has the right home for those businesses.

### 2a. Amendment (2026-09-24): the one-time review runs on `decisions/0024`'s classifier, not a manual spreadsheet pass

This is a stated change to §2's method, not a silent override of it — §2 above is left as originally written for its reasoning about sequencing and scope; this subsection records what changed and why once `decisions/0024`'s classifier existed to change it. §2's "spreadsheet or direct query" framing predates that classifier. Now that `decisions/0024` has built weighted-dictionary, tokenized classification with a confidence score per category, running the 121 "Other" records through it — rather than by hand — gets the same one-time result with less manual effort and a machine-checkable trail, and is the mechanism this pass now uses.

**Threshold coexistence, stated precisely so it isn't read as a conflict with `decisions/0024`:** this one-time bulk pass uses a **60% confidence bar**, applied only to this specific, already-known, already-published batch of 121 records. `decisions/0024` §3's 80%/50% thresholds remain the permanent standing rule for ongoing crawler intake and are unchanged by this. The two don't compete: 121 records currently sitting in a catch-all bucket with no category at all is a lower bar to clear than a live record already confidently assigned elsewhere that automation would be overriding, so a 60% bar is appropriate for pulling records out of "no real category" but would not be appropriate as the ongoing intake standard. Nothing here revises `decisions/0024`'s 80/50 default.

**Tokenization mechanism — reuses `decisions/0024` §2 as written, not a second mechanism:** the classifier compares whole tokens, not substrings — text is split into words first, and a candidate keyword (e.g. "bar") must match one of those tokens exactly, never match by appearing inside a longer token (e.g. "barbecue," "barbers"). Under whole-token comparison, "barbecue" tokenizes to the single token "barbecue," which is simply never equal to the token "bar" — there is no need to separately enumerate exclusions like "becue" or "bers," since a whole-token comparison never had a reason to match them. This is the same mechanism `decisions/0024` §2 already specifies for the newspaper/spa and anesthetist/esthet false positives; it is restated here only to make explicit that this bulk pass uses it as-is rather than a second, ad hoc exclusion-list approach.

**Audit trail for this pass:** each of the 121 reclassifications is logged with `previous_category` (i.e., "Other"), `assigned_category`, `confidence_score`, `classifier_version_or_ruleset_id`, and `timestamp` — enough to fully reconstruct which record moved where, under what confidence, and against which version of the dictionary, without needing a separate per-record human sign-off (per `decisions/0024` §4's reasoning: this is bulk metadata correction on already-published records, not new content clearing initial review, so `decisions/0005`'s staging gate doesn't apply here).

**Update (2026-09-24): the blocking dependency below is now resolved by `decisions/0028`.** The real, enumerated 24-group taxonomy this section previously said didn't exist anywhere in this document set now does — `decisions/0028`'s Refined 24-Group Level-1 Master Taxonomy. One consequence worth stating precisely rather than glossing over: `decisions/0028`'s group 24, "Local & Community Services," is a materially *narrower* concept than the old undifferentiated "Other" catch-all this section was written against — it's a strict fallback for businesses that genuinely span multiple category boundaries or serve a uniquely local/niche function, not "didn't keyword-match anything." That changes what this reclassification pass is actually doing: most of the 121 records are expected to land in a real group among `decisions/0028`'s 1–23, not simply move into group 24 under a new name. Only a record that genuinely doesn't reduce to any of groups 1–23 is a correct fit for group 24.

**Update (2026-09-24): groups 1–23 are the pass's primary targets; a group-24 result is never auto-applied, at any confidence score.** Stated as its own explicit rule rather than left implicit in the paragraph above: this bulk pass's job is to evaluate each of the 121 rows against the specific, substantive industries in groups 1–23 first — that's where a genuine keyword/dictionary match is actually meaningful, since those groups name real, bounded industries. Group 24 is different in kind, not just in size: because it's defined as the fallback for records that genuinely lack a single-industry fit, a classifier *scoring* a record into group 24 — even at or above this pass's 60% bar — is not the same kind of evidence as scoring it into, say, group 11. A dictionary match against "spans multiple boundaries" can't self-certify that the record actually does; only a human reviewing the record can confirm that. **So the rule is: any record the classifier would assign to group 24, regardless of confidence score, routes to the admin review queue instead of auto-applying** — the 60% threshold in the table below still governs auto-assignment into groups 1–23, but group 24 is never a silent, automatic destination, high confidence or low. This sits alongside, and doesn't replace, the already-established rule that a sub-60%-confidence result of any kind also routes to review (§2a above) — group 24 gets that same review-queue destination unconditionally, not just when confidence happens to be low.

### 3. Not an MVP-launch blocker, per `decisions/0021`'s own reasoning
Search and the directory already function correctly with "Other" as a valid, working group — a business in Other is still findable, still has a detail page (once `decisions/0020` Tier 2.1 ships), still returns in search. This is a categorization-accuracy problem, not a split-loop/completeness problem in the sense `decisions/0021` defined, so it doesn't gate launch the way that ADR's IN list does. It's worth fixing well before launch on quality grounds, just not because launch is blocked without it.

## What still needs to execute §2/§2a — the taxonomy-list blocker is resolved; one input remains

**§1 is done — the radius export gave real leaf categories and real business names, not a guess.** The taxonomy-list dependency that used to block §2/§2a is also now done: `decisions/0028` supplies the real, enumerated 24-group list, so the validation rule in §2a ("every `assigned_category` must match a string in the real taxonomy tree exactly") can actually run.

**What's still missing is narrower than before: identifying which specific live rows are the 121.** The shared CSV carries raw leaf-level category strings (`category` column) but no `category_id`/group-assignment column, so this file alone still can't say which specific database rows are sitting in the old "Other" bucket today. **What would close this precisely: a direct export of the 121 currently-"Other" rows (or their `category_id` values) from the live database** — the same requirement as before, just no longer entangled with also needing the group list, since `decisions/0028` now provides that half.

## Consequences

`architecture.md` §18 is updated to record this decision and now carries the full `decisions/0028` taxonomy directly. The group count moves from 23 to 24 Level-1 groups, and the "121 pending manual review" note is replaced with the actual resolution once it happens. §2a records that the execution method for that resolution shifted from a manual review pass to `decisions/0024`'s classifier (run at a one-time 60% bulk-remediation threshold, distinct from and non-overriding of that ADR's permanent 80/50 standing thresholds), with a five-field audit trail; `decisions/0024` itself is unchanged by this — it is referenced, not amended. `decisions/0028`'s group 24 ("Local & Community Services") is a narrower fallback than the old "Other," so most of the 121 are now expected to land in a real group among 1–23 rather than move into group 24 under a new name — the export named above is what lets that actually be executed rather than estimated.
