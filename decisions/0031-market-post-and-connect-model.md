# ADR 0031: Market Launches as a Post-and-Connect Model — No Transaction Processing at Launch

**Status:** Accepted (2026-09-25)

## Context

`decisions/0030` fixed Market as the fourth construct, built last, but deliberately left the actual commerce model open — the choice between the full merchant-of-record path and the narrower, payment-free framing already sketched in `future-considerations.md`'s Global Commerce / Marketplace Monetization entry. That choice is resolved here, per direction.

## Decision

Market's initial build is a **post-and-connect model, not a transactional marketplace**: a seller (personal or business) posts what they have — an item, a service, an offer — and an interested party expresses interest to connect. Traversence does not process payment, hold funds, or act as a party to the transaction at launch. Whatever happens next (price negotiation, payment, delivery or fulfillment) happens directly between the two parties, off-platform — the same way a claim or an inquiry through the existing Directory already works today.

This is the narrower framing `future-considerations.md` already sketched, now the actual chosen launch direction rather than one of two open options: it reuses the existing browse/search/claim patterns rather than building new commerce infrastructure, and because Traversence never becomes the payment-processing party, none of the merchant-of-record compliance machinery (VAT/OSS registration, landed-cost/duty engines, the GDPR/CCPA "targeting" questions `decisions/0025`/`decisions/0027` currently keep closed) is triggered by this launch version. It also matches the platform's founding "Living Connection Points" language (`charter.md`) and the speed-to-market/rural-access rationale already recorded for Market: a small or rural operator can start posting and connecting immediately, with no payment integration to build or wait on.

**Explicitly a first step, not a ceiling, per direction:** transactional processing — in-platform payment, and eventually the full merchant-of-record path `future-considerations.md` already scoped — is expected to be added as the platform grows. This ADR fixes where Market starts, not where it ends. When that expansion happens, it supersedes this ADR rather than amending it, per `workflow.md`'s append-only decision-log rule.

**Reference model, per direction (2026-09-25): Facebook Marketplace is the UX base for this build.** Concretely, that means: a browsable, filterable grid of posts (photo, price, title, location) as the default landing view; a location + radius filter reusing the same ZIP-centroid pattern the Resident/"Get Local" Directory search already uses (`architecture.md` §4 — no new geo mechanism needed); category-based browsing alongside search; a simple "Create new listing" posting flow; and personal "Buying"/"Selling" views scoped to the user's own posts and inquiries, sitting inside the existing personal account dashboard (`prd.md` Tier 1) rather than as a separate app section. "Connect" is the equivalent of Facebook Marketplace's message-the-seller action, not a "Buy Now" button — consistent with the no-transaction-processing decision above, since Facebook Marketplace itself doesn't process payment for the vast majority of its listings either.

**One deliberate scope boundary on the reference model, flagged rather than assumed:** "Facebook Marketplace is the base" applies to its browse/post/connect UX pattern, not to its ad-driven, engagement-ranked feed mechanics. `decisions/0007` (paid tiers never buy ranking) and the Charter's "Counter-Reaction to Algorithmic Bloat" section both already commit this platform to visibility earned through the existing Trust-Weighted model (`architecture.md` §7), never through payment or engagement signals — so "Today's picks" ordering, promoted/boosted posts, or any pay-to-appear-higher mechanic are explicitly out of scope for Market's launch build, even though Facebook's own version of this surface uses exactly that kind of ranking. If a future design pass wants a "picks" or "featured" surface, it needs to earn that placement through the same trust-score mechanism every other part of the platform already uses.

**Item detail page, per direction (2026-09-25) — the individual post view, same reference model:** title, price, and a "Listed [X] days/hours ago in [City, State]" line; a photo gallery with a thumbnail strip; structured fields (e.g. Condition) alongside a free-text description; and the "connect" action surfaced twice — a primary "Message" button near the top, and an inline quick-message composer lower on the page pre-filled with a low-friction starter line (Facebook's is "Hi, is this available?"). No "Buy," checkout, or price/quantity-selection control anywhere on the page, consistent with the no-transaction-processing decision above. Seller identity is a separate "Seller details" view rather than inline on the post itself, mirroring how a Directory listing keeps operator identity and listing content as related-but-distinct information.

**One privacy detail worth adopting deliberately, not by default — location on a Market post shows an approximate area, not an exact address.** Facebook's item page shows a location label and an approximate-radius map rather than a pinpoint address, which matters more for Market than for the Directory: a Directory listing is a business with a public storefront address by definition, but a personal (C2C) Market seller is very likely posting from their own home. Showing only an approximate area for personal posts — while a business posting through its verified listing can still show its real, already-public business address — is a real, previously-undocumented safety distinction between how location works on the two constructs, and should be built as the default for personal Market posts rather than left to whatever the Directory's existing location display happens to do.

**Delivery/handoff is explicitly not a platform function, per direction.** Consistent with the no-transaction-processing decision above, Traversence doesn't coordinate shipping, meetup logistics, or delivery for a Market post — the two parties work that out directly once connected, the same way price and payment are negotiated off-platform. The approximate-location default exists so a buyer has enough to judge distance/convenience before connecting, not to support in-platform delivery coordination.

**The approximate-location default is an opt-out, not a hard limit, per direction (2026-09-25) — this is the confirmed second use case for `future-considerations.md`'s Residency / White-Pages Address Index entry.** A personal seller who wants their real address visible instead of the default approximate area should be able to choose that, using the same voluntary, opt-in, user-supplied address field that entry already recommends building (for the separate rural-delivery problem) rather than the full residency-index product. Approximate-by-default, real-address-by-explicit-choice mirrors the opt-in posture `decisions/0010` already uses for AI-consumption consent — the safer state is default, the more exposed state requires an affirmative choice, never the reverse.

## Consequences

`future-considerations.md`'s Global Commerce / Marketplace Monetization entry is updated: the narrower framing is no longer just a related idea, it's the adopted launch direction, and the full merchant-of-record path is now explicitly the future-expansion case rather than a live open choice.

`prd.md`'s Tier 2.8 gains its real minimum feature shape for the first time: a posting flow (what a seller has to offer), a browse/search surface (reusing Directory patterns), and a "connect" action (routing an interested party to the seller — likely via the same messaging/inquiry mechanism the Centralized Communications Center already provides, `architecture.md` §5, `prd.md` Tier 2.5) — still needing its own schema and design pass, but no longer an undefined placeholder. No payment, escrow, checkout, or order-management surface is built at this stage.

`decisions/0002`'s dual-accounting model and `decisions/0008`'s dual-attribution rules apply to Market posts the same as any other write — a post is stamped with `actor_user_id` and, where posted on behalf of a business, the `entity_id` the `listing_access` check authorized. Trust and safety for Market posts inherit the existing HITL guardrails (`decisions/0005`) and the user-side block/filter/report controls (`prd.md` Tier 2.4) rather than needing a new moderation model built from scratch.
