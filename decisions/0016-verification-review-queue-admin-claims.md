# ADR 0016: Verification Review Queue — `admin/claims.php`

**Status:** **Amended by `decisions/0070` (2026-10-09):** the claims queue now holds claims, texts, calls, holds and disputes. Accepted (2026-09-23), extends `decisions/0015`'s Tier 4 intake by building the reviewing side it deliberately deferred. Reconciled against `admin/adminportal.php` (real, live placeholder shell) and a newer copy of `api/lib/Auth.php` found in a different upload than the one earlier ADRs in this set were checked against — see the flagged discrepancy below. **Revised twice same day, per direction:** adds manual, admin-performed phone verification as a real tool in this queue — see item 4 below — rather than leaving phone verification as pure future work waiting on third-party telephony infrastructure; then wired up against `decisions/0017`'s new real document-upload capability, so `has_document` on this queue's decisions reflects an actual uploaded file rather than only a manually-ticked checkbox.

## Context

`admin/adminportal.php` is itself a real, labeled placeholder ("PLACEHOLDER: admin home... every tile except those marked live is a stand-in"), and one of its six tiles is already named **"Claims — Ownership verification queue."**, pointed at nothing (`$href = null`, rendered "Not built yet"). This ADR is that tile.

**A real discrepancy worth flagging plainly:** `architecture.md` §11 already documents a set of hub/listing-scoped `Auth.php` helpers (`canAdministerHub()`, `requireHubAdmin()`, `isSuperAdmin()`, `requireSuperAdmin()`, `getListingPermission()`, `requireListingAccess()`, `hasAnyAdminAccess()`) as real and live. They're real — but not in the `api/lib/Auth.php` copy inside the `website-20260923_1.zip` export prior ADRs in this round (0012, 0014, 0015) were checked against, which has only `requireAdmin()` (the legacy `is_admin`-gated one). A separate, later-dated copy (`traversence-session-delivery.zip`, the same nested archive the master platform spec came from) has the full 537-line version with every one of those helpers implemented. The session-delivery copy is newer (Sep 14 vs. Sep 12) and matches what `architecture.md`/the master spec already describe as shipped, so this ADR is built against it — but it means at least one of the exports Jason has floating around is stale relative to what's actually running, worth a quick "which zip is really current" check outside this document set.

The helpers this ADR actually needs, confirmed real in that newer copy:
- `hasAnyAdminAccess(int $userId): bool` — any `admin_access` row at all.
- `canAdministerHub(int $userId, int $hubId): bool` / `requireHubAdmin(int $hubId)` — `super_admin` (hub_id IS NULL) or `regional_admin` scoped to that specific hub.
- `isSuperAdmin(int $userId): bool` / `requireSuperAdmin()`.

The hub chain an entity resolves through: `entities.micro_cluster_id → micro_clusters.geo_hub_id → geo_hubs.hub_id`, matching `admin_access.hub_id`.

The queue this page reads pulls from two tables, now with three real, distinct row-types after `decisions/0015`: `verification_attempts WHERE status = 'pending'` covers Tier 2's auto-flag (`method = 'admin_override'`, entity already `verified`, retroactive/audit-only) and Tier 4's claimant-facing intake (`method = 'admin_override'`, entity still `claimed-unverified`, waiting on a first decision); `disputes WHERE status = 'open' AND` the filer never cleared `decisions/0015`'s precursor check covers third-party filings still awaiting a first human look before they're allowed to affect the listing's display at all. All three need different actions, not one generic "approve/reject."

## Decision

**One page, hub-scoped, matching the plan `adminportal.php`'s own banner already states** ("Admin access is hub-scoped in the plan... a regional admin sees only their hub"):

- **`admin/claims.php`** — gated by `Auth::hasAnyAdminAccess()` to enter at all. The list query joins `verification_attempts → entities → micro_clusters → geo_hubs` and filters to the calling admin's hub via `canAdministerHub()`'s own logic (super_admin: no filter, sees everything; regional_admin: `geo_hubs.hub_id = `their hub). Sorted oldest-first — plain FIFO, no priority scoring. **Note, revised same day (`decisions/0015`):** an earlier version of this note gave an unresponsive-claimant dispute row queue-priority; that's superseded — per direction, an unresponsive claimant now auto-resolves the case (`claim_abandoned`) rather than sitting in this queue waiting for a human look, so there's no longer a row here to prioritize in that specific situation. The queue stays plain FIFO with no priority-scoring exception.
- **Three row types, three action sets**, distinguished by row source and the target entity's current `status` (no new column needed):
  - **Tier 4 intake row** (entity still `claimed-unverified`): **Approve** calls the already-real `Verification::applyAdminVerification($pdo, $entityId, $adminUserId, $hasDocument)` — `$hasDocument` is now pre-filled from whether a real `verification_documents` row exists for the request (`decisions/0017`, same day: uploads are real now, stored outside the webroot, viewable only through this hub-scoped queue), with the manual checkbox kept as a fallback for the rare document that still arrives by email instead — then marks the originating `verification_attempts` row `status = 'approved'`, `resolved_at = NOW()`, `reviewed_by_user_id` = the admin. **Reject** marks the row `status = 'rejected'` with the same fields plus a required short admin note (emailed to the claimant so they know to try another tier or resubmit with more information); the entity stays `claimed-unverified` — rejection here is a non-event for the listing, not a penalty.
  - **Tier 2 retroactive-audit row** (entity already `verified` via 3+ referrals): this is oversight on an *already-live* verification, so the two admin actions are asymmetric on purpose. **Looks legitimate** simply marks the row `approved`/resolved — no entity change, nothing else happens. **Flag as fraudulent** does **not** instantly revoke a live, public listing on one admin's say-so — it opens a real `disputes` row instead (`decisions/0015`'s mechanism, `filed_by_user_id = NULL` — the nullable field that exists specifically for an admin-initiated dispute, `reason` = the admin's note), giving the claimant the same challenge-deadline/re-verify-at-Tier-3+ opportunity a peer-filed dispute would, rather than a silent, one-click, no-appeal takedown. The retroactive-review row is marked `rejected` with a note pointing at the new dispute's id, so the audit trail reads as "flagged → escalated to formal dispute," not "flagged → resolved."
  - **Unproven dispute-filing row** (new, per `decisions/0015`'s precursor-check revision — an `open` dispute whose filer never cleared the standing/domain-match check): the entity's display hasn't been touched yet, so there's more room here than the other two rows. **Escalate** flips `entities.status = 'disputed'` (limited display begins) and starts the normal `challenge_deadline` countdown from that moment, same as if the filer had cleared a fast path themselves. **Dismiss** marks the `disputes` row `resolved` with an admin note; the listing was never touched, so dismissal is a true no-op for it, not a reversal.
- **One decision endpoint**, matching this codebase's own established `action`-field convention (`listing/api/claim.php`'s `start`/`confirm`): **`POST /admin/api/claims/decide.php`** with `{row_type: 'verification_attempt'|'dispute', row_id, action, note?, has_document?, phone_verified?}` — `action` is `'approve'|'reject'` for a `verification_attempt` row, `'escalate'|'dismiss'` for a `dispute` row. It re-derives the entity's hub from `row_id` server-side and calls `Auth::requireHubAdmin($hubId)` (or accepts a `Auth::requireSuperAdmin()` pass) itself — never trusting the page's own filtering as the real access control, the same principle every other real endpoint in this codebase already follows (CSRF + server-side re-check, not client-side gating).

### 4. Manual phone verification — an admin's own tool, not a third-party integration, built now
`decisions/0015` flagged phone-based verification as real, worthwhile, and genuinely blocked — the codebase has no SMS/voice provider anywhere, and standing one up is its own infrastructure decision. **Per direction, that gets unblocked without waiting for that integration: the phone call happens, it's just the admin who places it, not an automated system.** Concretely: any admin reviewing a row in this queue — a Tier 4 intake request or an unproven dispute filing — gets a **"Called listed number"** field on the same decision they're already making (`phone_verified: true|false|null`, plus a note on who was reached and what was confirmed). This is a real regional- or system-admin action, gated by the exact same `Auth::requireHubAdmin()`/`requireSuperAdmin()` check every other action in this ADR already uses — a regional admin can only phone-verify listings in their own hub, matching the "admin access is hub-scoped" plan `adminportal.php` already states.
- **For a Tier 4 intake row:** a confirmed call is exactly the kind of evidence `Verification::applyAdminVerification()` was built to act on — the admin approves as already specified in item 2 of the Decision above, with the call itself recorded in that approval's notes (no schema change: `notes` on the `verification_attempts` row this creates is already free text).
- **For an unproven dispute-filing row:** a confirmed call gives the admin a real basis to escalate or dismiss with actual evidence behind it, rather than judging the written `reason` alone — recorded the same way, in the resolution note.
- **Explicitly the interim measure, not the end state.** This is deliberately positioned as a stand-in for the eventually-desired automated SMS/voice OTP `decisions/0015` already flagged as the stronger long-term direction (real listings have `phone` populated far more often than `website`) — it ships now because it costs zero new infrastructure or vendor spend, only admin time, and gets replaced or supplemented once a real telephony integration is actually affordable. Nothing about this ADR's schema or endpoint contract needs to change when that day comes — `phone_verified` stays meaningful either way, whether a human or an automated system produced it.

## Consequences

`admin/adminportal.php`'s "Claims" tile gets its real `href` now, becoming the first of its six tiles to go from stand-in to live (per its own placeholder banner listing "Categories" as the only other currently-live one).

This ADR does not build a review UI for `admin/listings.php`, `admin/users.php`, or any of adminportal.php's other four still-stand-in tiles — it is scoped to the one tile Jason asked for. The other tiles remain exactly as flagged in `routes.md` already.

The Tier 2 "flag as fraudulent → opens a dispute" path means an admin can never instantly strip a live verified listing without going through the same challenge window a peer-filed dispute gets. Since `decisions/0015`'s same-day revision, that window no longer removes the listing from search entirely — it reverts to limited display (badges and owner-supplied content hidden, listing itself still fully visible) — so an admin's fraud flag carries that same, now-proportionate consequence rather than the fully-hidden one this ADR was originally written against.

The Auth.php version discrepancy above is worth resolving independent of this document set — this ADR builds against the newer, more complete copy because it matches what's already documented as shipped, but if the live server is actually still running the older `full-export` copy, `admin/claims.php` (and, more importantly, `decisions/0015`'s `listing_access` write in the claim flow) would need those hub/listing helpers deployed first.
