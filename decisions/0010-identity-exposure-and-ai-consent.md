# ADR 0010: User Identity Exposure, Public Authorship, and Consent Controls for AI-Engine Use of Contributions

**Status:** Accepted — fully resolved as of 2026-09-24. The one implementation parameter this ADR originally left open (the AI-consumption control's default state) is now decided; see the revised Decision and Consequences below.

## Context

User IDs are the backbone of accountability across the platform. ADR 0002's dual-accounting model, ADR 0008's downstream attribution guarantee, and the Trust-Weighted Interaction Mechanics (`architecture.md` §7) all depend on activity being traceably tied to a real identity rather than an anonymous one — that traceability is what rules out sock-puppeting, anonymous bias, and pay-to-play manipulation (§21). It's a deliberate design choice: users log in, the ID aggregates their activity, and that ID is the reference point that resolves credibility questions and lets a user point back to their own prior contributions.

That same traceability creates a real, separate risk: a user whose contributions (a critical review, a reported issue, a community post) are visibly and permanently tied to their identity can be targeted for harassment or retaliation because of what they said. Accountability and user safety pull in opposite directions here, and three questions followed from that tension: whether the raw ID should ever be the *visible* source label on content, whether identity should travel into AI systems that consume user activity, and whether users can look up or track each other by ID.

## Decision

**Transparent authorship via profiles, not raw IDs.** Public-facing content (comments, reviews, contributions) is attributed to a user's front-end profile — the existing `/user/` profile already described in §6 — not to the raw `actor_user_id`. This gets the credibility and accountability benefit of visible authorship without exposing backend database identifiers. The profile is discoverable by other users (consistent with the platform's community-transparency goals — a profile is public by design), which resolves the earlier open question about cross-user lookup: yes, users can find and view each other's public contribution history through profiles; that visibility is the point of a profile, not a bug to prevent.

**Safety is handled through user-side control, not identity concealment.** Rather than hiding who said something to prevent harassment, the user who's being targeted gets tools to act: block a specific user, filter unwanted engagement, and report or request removal of abusive interaction directed at them. This is the platform's actual answer to the "weaponization" risk raised earlier — control shifts to the person being targeted, rather than the platform trying to make contributors anonymous (which would undercut the accountability the whole trust model depends on).

**The raw ID stays a strictly internal accounting mechanism.** Behind the profile, `actor_user_id` continues to be logged and tracked exactly as ADR 0002 and ADR 0008 require — for data integrity, trust scoring, dispute resolution, and moderation — but it is never itself the public-facing identity. This is the concrete resolution to the "internal reference vs. public byline" distinction raised in the prior version of this ADR: the profile is the public layer, the ID is the plumbing underneath it, and the two are cleanly separated by design rather than by convention.

**De-identify by default for AI grounding material.** When a community contribution is used as input to an AI-generation system (topic extraction, article drafting, the Personalized Insight & Productivity Engine, §23/§26), the content's substance may be used without carrying the contributor's profile identity into that pipeline — the informational value of a how-to explanation or a described use case doesn't depend on who wrote it. Identity only needs to travel with the content when a system would actually surface or rely on *who* contributed it.

**Explicit opt-in where identity would be attached to AI use — resolved 2026-09-24, per direction.** For the narrower case where a system would associate a user's profile identity with AI-engine output (crediting a named contributor, or feeding a specific person's own activity into their own personalized insights, e.g. §23's Personalized Insight & Productivity Engine), the control defaults to **off**. A user's identified activity is never fed into that kind of AI pipeline until they actively, intentionally turn it on — separate from the dual-accounting attribution required to run the platform itself, which isn't optional. A user cannot opt out of `actor_user_id` being stamped on their own writes; whether that identified activity ever reaches an AI pipeline beyond the platform's core operation is theirs to grant, not theirs to revoke after the fact.

**Resolved — the parameter this ADR originally left open:**

- **Default state for the AI-consumption control: opt-in, decided 2026-09-24, per direction.** Reasoning given directly: this is the stricter, more privacy-protective posture, it's the easier position to defend under GDPR-style consent standards, and it keeps the compliance framework clean from day one rather than needing to be tightened later once real usage exists. It also composes cleanly with `decisions/0011`'s data-minimization rule — an opt-in default means the Personalized Insight & Productivity Engine (§23) starts with *zero* identified users in its pipeline until each one actively grants it, which is the most conservative possible starting state for a feature that also has to satisfy the classify-at-intake, abstraction-out rule. The trade-off named at the time (opt-out would likely yield more usable grounding data) is accepted as the real cost of this choice, not overlooked.

## Consequences

`architecture.md` §7, §11, §23, §25, and §26 all need to reflect profile-based authorship and admin-vs-steward role separation (see §11's actor definitions) rather than raw-ID exposure. A user-facing blocking/filtering/reporting feature is a real, previously undocumented product requirement — it belongs on `prd.md`'s roadmap, not just in this ADR (see `decisions/0020`'s Tier 2.4, which already sequences it). `architecture.md` §24's GDPR/CCPA disclosure position now names the AI-consumption **opt-in** control as a required disclosure, with its default state now fixed rather than pending. De-identified AI grounding material (the default case for content generally) needs no consent gate; only identity-attached AI use does, and that use now starts from off, not on.
