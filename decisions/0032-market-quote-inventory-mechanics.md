# ADR 0032: Market Quote & Inventory Mechanics — Dual-Confirmation Completion, Item Pricing Fields, Tiered Catalog Depth

**Status:** Accepted (2026-09-25)

## Context

`decisions/0031` established Market as a post-and-connect model with no in-platform transaction processing. It deliberately left the shape of the "connect" mechanism loose — a generic messaging action. Per direction, the actual mechanism needs to be a real Quote workflow with pricing fields, completion semantics, and tiered catalog depth, not a bare message thread. This ADR settles that shape.

## Decision

**Item pricing fields, mirroring the private/public split `listing_access` already enforces.** A Market item carries cost, markup, and a tax/no-tax flag. Cost and markup are private — visible only to the listing's own owner/manager via `listing_access`, the same boundary that already keeps a business's internal data off the public directory. The computed price and tax status are what's public-facing. This lets a business (personal or B2B) manage real internal margin data through the same posting flow, without exposing it. **Markup structure, per direction 2026-09-25: both a flat dollar amount and a percentage are supported, per item** — a seller picks whichever fits a given item rather than the platform forcing one single markup format.

**Response-time expectations are self-defined per listing, per direction — not a platform-enforced SLA.** A business inputs its own sales process (the steps it follows once a lead comes in) and its own target response time within its listing profile, rather than the platform holding every listing to one universal standard. Actual response times (tracked via Quote timestamps and `decisions/0036`'s per-listing routing) are shown against that self-defined target, giving a business and its customers a real, comparable expectation without Traversence dictating what that expectation should be.

**Quote is a first-class, stateful object, not a message.** Requested → Accepted / Rejected, the same pattern `decisions/0015`'s claim/dispute workflow already established for a real state machine sitting alongside — not built out of — the messaging system. This is what makes "mark sold and manage inventory" possible: something concrete has to change state for an item's status to update.

**Completion requires dual confirmation, per direction — not self-report.** A self-reported "sold" status is gameable: a seller could mark items sold with no real transaction behind it, inflating apparent activity. Instead, both parties confirm — the seller confirms "sold," the buyer confirms "bought" — and only when both have confirmed does the Quote move to Completed. This is a real, mutually-attested event, not a claim either party can make unilaterally.

**Quote completion is Market's first review/rating anchor point, per direction.** No review or rating system exists anywhere else on this platform today — Directory listings have none. A completed, dual-confirmed Quote is a verified interaction between two real accounts, which makes it a meaningfully stronger foundation for reviews and ratings than an unverified review a visitor could leave without proof of any interaction at all. Issue/dispute reporting on a specific transaction anchors to the same completed Quote record, following the same non-destructive, status-based pattern `decisions/0015`'s dispute flow already uses rather than inventing a new one.

**Inventory status updates on completion, non-destructively.** An item tied to a completed Quote is marked sold (a status flag, matching the `entities.status` enum pattern already used elsewhere) rather than deleted — preserving it for history and for the review/rating record that references it.

**Catalog shape differs by seller type, per direction:**
- **Personal (C2C) sellers get a streamlined, single-item flow** — one item up, one item sold, no catalog-management UI. This matches how an individual actually uses a marketplace (posting what comes up, not running an ongoing storefront) and needs no tier gate — it's core, free, same as Directory access itself.
- **Business listings get the fuller multi-item catalog**, sized by tier and bounded by a single per-listing cap. **Per-listing cap: 250 items, on every individual Cornerstone listing** — a ceiling on one listing alone, per direction 2026-09-25. **The combined/group cap is removed, per direction 2026-09-25** — an earlier version of this ADR also capped a Location Group's (`decisions/0036`) combined total at 500 items across linked listings; that's dropped. Linking listings into a Location Group is purely about shared searchability, admin visibility, and communications oversight (`decisions/0036`) — it has no effect on catalog capacity. Each linked listing simply keeps its own independent 250-item cap, so there's no combined ceiling to hit and no conflict to resolve when previously-unlinked listings (each already near or at 250) get linked together later. Core and Strategic's per-listing cap remains open — this resolution covers Cornerstone only, since that's the tier the deciding case (SJ Portables) actually runs on.
- **Multi-location inventory management is Strategic/Cornerstone-only, per direction** — mirroring the existing multi-location billing boundary in `commercial.md` §10 (Core stays strictly single-location). Per `decisions/0036`, it applies only to listings an account has explicitly linked into a Location Group — never inferred just because a user's `listing_access` grants happen to span multiple listings, and never to a stale or unclaimed listing.

## Consequences

`prd.md` Tier 2.8 gains real schema requirements: a `market_items` table (or equivalent) with cost/markup/tax fields and a status enum, and a `quotes` table with a status enum and dual-confirmation timestamps — both still needing their own technical-design pass, but no longer undefined. A new review/rating capability is introduced to the platform for the first time, scoped initially to completed Market Quotes; whether it ever extends to Directory listings generally is a separate, later question, not decided here. `decisions/0002`/`0008`'s dual-accounting and dual-attribution rules apply to every Quote and review the same as any other write. `commercial.md`'s tier structure gains a new axis to formally size (catalog depth) — Cornerstone's is now set (250 per listing, above, with no separate group cap); Core and Strategic still need their own numbers before this axis is fully resolved. The multi-location scoping mechanism itself — how listings actually get linked into a group the caps and admin views operate over — is `decisions/0036`, not this ADR. **Explicit scope boundary, added 2026-09-25:** every item this ADR describes is a single SKU — no parent-product/variant model (e.g., one shirt product with size/color variants) exists yet, and the catalog caps above count items as posted under that single-SKU assumption. Raised while scoping SJ Portables (which doesn't need variants) but flagged as a real future gap for a different kind of seller — see `future-considerations.md`'s "Product Variants / Multi-SKU Items" entry, not designed here.
