# ADR 0039: External Source Plug-in Model & Multi-Model Pricing Typing — Generalized From SJ Portables/ShedSuite

**Status:** Accepted (2026-09-25)

## Context

While bridging SJ Portables' concrete technical FRD (its ShedSuite integration for ABCO shed inventory) with this build's Traversence-platform framing, the integration designed for ShedSuite — a scheduled inventory/pricing pull, a unified catalog combining externally-sourced and natively-priced items, and an order-processing hand-off back to the external system at Quote-Accepted — was recognized as a pattern that isn't specific to SJ Portables or to ShedSuite. Per direction, any listing whose inventory or pricing truth lives in a third-party system could plug that system in the same way, under one general contract rather than bespoke, per-integration code. Per direction, one of the platform's biggest potential advantages from this pattern may not even be in the dealer-inventory space it was designed for — it applies directly to existing OTA (Online Travel Agency) integrations for Traversence's original Discovery/travel side of the platform, where a listing's live availability and pricing already lives in a channel manager or OTA feed the same shape of problem as SJ Portables' shed inventory living in ShedSuite.

Separately, reviewing real pricing-rendering examples (per direction) surfaced that `decisions/0032`'s original "cost, markup, tax flag" catalog model is not expressive enough on its own. Markup-on-cost and margin-on-price are different calculations that produce different results from the same stated percentage — 50% markup on a $20 cost renders $30; 50% margin on the same $20 cost renders $40 — and real merchants use both, often without realizing they're different math. A fee-inclusive ("marketplace fee") model needs to fold in variable costs like shipping and platform/referral fees before a target markup or margin is applied. Variant-level items — already flagged as a schema gap in `prd.md`'s Tier 2.8 entry ("the current Market item schema is single-SKU only") — need cost and price computed per attribute combination, not per top-level SKU. And bundles need their own pricing logic operating across multiple underlying items, not any single item's cost.

## Decision

**A generic External Source contract, configurable per listing or per product line — not hardcoded to any one integration.** Each configured source defines: a sync cadence for pulling live inventory/pricing; a field mapping from the source system's data shape into Traversence's catalog fields; a `pricing_model` tag (below) describing how that source's items are priced; an order hand-off mechanism back to the source system, fired when a Quote on one of its items reaches Accepted (the specific mechanism — an active API push, versus a hand-off link with inbound webhook status updates — is configured per source, since different third-party systems support different integration shapes); and an inbound webhook contract for status updates from the source system. A listing can combine one or more External Sources with its own natively-priced catalog in a single unified catalog and a single Quote process (`decisions/0032`), exactly as SJ Portables combines ShedSuite-sourced sheds with its own natively-priced containers, tanks, septic, and culverts. **SJ Portables/ShedSuite is this contract's first real-world instance, and its hand-off mechanism is now confirmed against ShedSuite's actual published API spec (`https://app.shedsuite.com/api/docs/index.html`), per direction 2026-09-25.** The real call sequence is: create the ShedSuite customer once via `POST /contacts/v1`, then create the transaction via `POST /quotes/v1`, referencing that customer, the dealer, and the building configuration (model variation, add-ons, colors, and optionally a `design` reference pointing back to a configuration produced in ShedSuite's own 3D builder). That call computes real pricing and returns an `orderNumber` immediately — meaning it functions as the actual order-creation call despite being named "quote" in ShedSuite's API, not a separate pre-order stage needing later conversion. Downstream status is then read back via `GET /customer-orders/v1`, a far richer object (status, delivery dates, RTO terms) than the Quote object itself. **Correction, per the actual spec:** there is no webhook-registration endpoint anywhere in ShedSuite's published API — the "real-time webhooks" capability described in ShedSuite's own marketing material is not present in this spec, so status sync should be designed as scheduled polling of `GET /customer-orders/v1` (filterable and sortable by `lastUpdated`) rather than assumed as inbound push, unless ShedSuite confirms a separate, non-API webhook-configuration channel exists. Dealer/lot scoping is confirmed workable at the query level regardless of token scope: `dealerId` and `locatedAtDealerId` query parameters exist on the Quotes, Customer Orders, and Inventory endpoints respectively. The remaining open item for SJ Portables specifically stays an account-structure question, not a technical one: whether SJ Portables — versus ABCO, as the umbrella ShedSuite account holder — can generate or hold its own token (the `scopes` field on token creation is undocumented as to whether it can restrict a token to a specific dealer).

**Explicitly named future application, per direction: existing OTA integrations.** This contract is not scoped to dealer/retail inventory sources. A Discovery-side listing (a hotel, vacation rental, or other travel business) whose live availability and pricing already lives in an OTA channel manager is the same shape of problem — an external system as source of truth for some or all of a listing's inventory — and should be able to plug into the same External Source contract rather than needing a separate integration model built later. This is flagged as a named future use case, not built now; SJ Portables/ShedSuite remains the contract's first built instance.

**A `pricing_model` tag per catalog item (or per bundle), expanding `decisions/0032`'s original cost/markup shape into a real, multi-model set, per direction:**

- **`cost_markup`** — retail = cost × (1 + markup%), and/or cost plus a flat-dollar markup; `decisions/0032`'s original shape. Profit is computed as a percentage of cost.
- **`cost_margin`** — retail = cost ÷ (1 − margin%). Explicitly distinct from `cost_markup`, never a synonym or a UI relabeling of it: the same stated percentage produces a different retail price under each model (50% markup on $20 cost renders $30; 50% margin on the same $20 cost renders $40), so the schema must record which calculation the merchant actually means and never infer one from the other.
- **`landed_cost_plus`** — the "marketplace fee" case: variable costs beyond base product cost (shipping, a platform/referral fee expressed as a percentage plus a flat per-transaction amount) are added to cost before either a markup or margin target is applied. A superset computation of the two models above, with extra fee inputs.
- **`variant_priced`** — not a pricing formula on its own, but a schema requirement: cost (and therefore retail, under whichever of the above models applies) is computed per attribute combination — size, color, material, and so on — rather than per top-level SKU. This is the real shape of `prd.md`'s already-flagged "Market item schema is single-SKU only" gap, resolved here rather than left a placeholder.
- **`bundle_priced`** — a distinct object, not a per-item model: a bundle references multiple underlying catalog items and prices the combination directly, under one of several bundling strategies — a straight percentage off the combined value, a flat dollar amount off the combined total, or a fixed tiered price for choosing any set number of items from a group. Bundle profit is computed against the bundle's total underlying cost, never any single item's.
- **`build_to_order`** — no static catalog price; price resolves only once specific configuration options are chosen, often (as with ShedSuite's 3D builder) entirely outside Traversence's own Quote flow. The catalog shows a starting ("from $X") price only.
- **`mirrored`** — price is fully set and owned by an External Source, read-only; Traversence performs no local computation on it at all (SJ Portables' ABCO shed items via ShedSuite).

## Consequences

`decisions/0032`'s catalog item shape needs a `pricing_model` field and the additional inputs each model requires (fee percentages and flat amounts for `landed_cost_plus`, a variant-attribute dimension for `variant_priced`, a bundle-membership shape for `bundle_priced`) — a schema extension, not a reversal of anything already decided there; cost stays private to owner/manager and only the computed price and tax status are public, under every model. `prd.md`'s Tier 2.8 "Product variants... flagged 2026-09-25" entry is resolved by `variant_priced` rather than remaining an open placeholder. The External Source contract itself needs its own schema (source configuration per listing, field-mapping definitions, the hand-off-mechanism and webhook shapes) — not yet designed, flagged here rather than assumed, the same "not yet schedulable" caveat other structural gaps in this decision log carry. SJ Portables' BRD documents this contract's first instance (ShedSuite); a future OTA-integration build would be this contract's second instance and should not require its own separate integration model.
