# ADR 0014: Registration Flow — Email-Verification Gate Before Any Session

**Status:** Accepted (2026-09-23), reconciled directly against the real live code and schema (`register.php`, `login.php`, `verify-email.php`, `api/lib/Auth.php`, `api/lib/Mailer.php`, the `users`/`email_confirmations` tables in the live database export). **Revised 2026-09-24, per direction: registration now also captures the AI-personalization opt-in control `decisions/0010` requires, designed to be a single, low-friction toggle rather than a separate task.** See the new subsection below.

## Context

The current registration surface is a placeholder — real enough to click through, not a finished flow. Reading the real code and schema directly:

- The form captures display name (optional), email, and password. Its client-side copy says "Password (10+ characters)" with `minlength="10"`, but the server-side rule actually enforced by `Auth::assertPasswordMeetsRequirements()` is different: 8+ characters, at least one uppercase letter, one lowercase letter, one number, and one special character. The two disagree, and the accurate rule is the server one.
- `Auth::register()` validates email format and password strength, inserts the `users` row, and calls `issueEmailConfirmation($userId, 'registration')` — which creates a real, live `email_confirmations` row (`action_type = 'registration'`, token, expiry). But nothing today actually sends that confirmation email, and nothing prevents the account from being used before it's confirmed.
- `Auth::attemptLogin()` doesn't check `email_verified_at` at all before creating a session — it authenticates on password alone and simply reports `email_verified` as an informational boolean to the client afterward.
- No terms-of-service / consent flag is captured or stored anywhere in the flow.
- `Auth::register()`'s own code comment already flags an open question: the `users.role` column (`ENUM('admin','business_owner')`) has no "plain resident" value, so every new registrant silently gets the table's `business_owner` default regardless of why they signed up. A direct grep of `api/` confirms this is pure data mislabeling, not a live authorization gap — `business_owner` is never checked as a gate anywhere in the codebase, and `requireAdmin()` gates on the separate `is_admin` column alone, not `role`.
- The pieces to close the gap already exist and just aren't connected: `verify-email.php` (the page) already calls a `POST /api/auth/verify-email.php {token}` contract; `Auth::confirmEmailToken()` already exists server-side to resolve that token; `Mailer.php` already sends authenticated mail through a real mailbox. This is a wiring gap, not a missing-infrastructure gap.

## Decision

Registration becomes a real, verification-gated flow, built from the pieces above rather than new mechanism:

- **New required field: Terms of Service / Privacy Policy consent.** The registration form adds a required checkbox; `POST /api/auth/register.php` rejects the request (422) when the flag isn't `true`. No new table is needed — the `email_confirmations` row already created for that `registration` action, with its own `created_at`, is sufficient acceptance provenance.
- **Password policy display corrected, not changed.** The already-enforced server-side rule (8+ characters, upper, lower, number, special character) is what gets shown to the user, as a live checklist rather than static placeholder copy — the stale "10+ characters" text and `minlength="10"` are removed.
- **No session is created at registration.** `Auth::register()` already doesn't create one; this ADR keeps that behavior and makes it deliberate rather than incidental.
- **Registration blocks on email confirmation before any session.** Of the options considered (no gate; gate writes but allow browsing; gate everything), this is the strictest: `Auth::attemptLogin()` gains a real check — if `email_verified_at IS NULL`, the login attempt is rejected with a clear, actionable message ("Please confirm your email before signing in — check your inbox for the confirmation link") instead of silently succeeding as it does today.
- **The confirmation email gets sent.** `POST /api/auth/register.php`, after `Auth::register()` succeeds, sends the confirmation email through `Mailer.php`, linking to the existing `/verify-email.php?token=...` page, which already drives the existing `Auth::confirmEmailToken()` contract. This connects three real, already-built pieces that were never wired together end-to-end — it does not invent new infrastructure.
- **A resend-confirmation path is added.** Because `email_confirmations.expires_at` makes a stale token a real, expected case, the login page shows a "Resend confirmation email" action specifically when login fails for the new unverified-email reason. It re-runs `issueEmailConfirmation($userId, 'registration')` and re-sends via `Mailer.php`; an earlier unconfirmed token for the same user/action is simply superseded by the newest one rather than individually invalidated, since `confirmEmailToken()` resolves by token value and the old token was never the one actually delivered to the user's inbox last.
- **The `role` default is corrected, not left alone.** `users.role` gains a third enum value, `user` (`ENUM('user','business_owner','admin')`), which becomes the column's new default; `Auth::register()`'s INSERT now sets `role = 'user'` explicitly rather than falling through to the old default. This matches the actor model already documented elsewhere in this governance set (`architecture.md` §11): every registrant starts as the base "Personal human user" actor, and becomes a business owner/manager only through an earned `listing_access` grant, never by registration default. `business_owner` and `admin` remain in the enum as legacy values already in use elsewhere; nothing currently reads or gates on `role = 'business_owner'` in the codebase, so this is a safe, non-breaking change — real authorization continues to run through `listing_access`/`admin_access` (and, for now, the separate `is_admin` flag), not `role`.

### AI-personalization opt-in at registration — added 2026-09-24, per direction: "since opt-in is safer, I would like to see how the create-user-account [flow] can address this and make opting in super easy"
`decisions/0010` requires the AI-consumption control to default off (opt-in) — that decision doesn't change here. What this adds is where and how a user actually gets to say yes, designed around making the *yes* path as close to frictionless as the *no* path (which requires no action at all, since off is the default).

- **New field: `users.ai_personalization_opt_in` (`BOOLEAN NOT NULL DEFAULT FALSE`), plus `ai_personalization_opt_in_at` (nullable timestamp, set only when the flag is actually turned on).** The column default being `FALSE` at the schema level — not just "the form defaults to unchecked" — matters on its own: it means even a bug that skipped rendering the toggle entirely would still leave a new account correctly opted out, never silently opted in by omission. This is the concrete piece of `decisions/0010`'s standing pre-work item (drafting the compliance framework early) that was actually schema-shaped, not just policy language.
- **One additional toggle on the registration form, visually and functionally separate from the required Terms/consent checkbox — never bundled with it.** Bundling an optional data-use choice into a required legal-acceptance checkbox is a real, well-known consent anti-pattern (it's how "consent" stops being genuinely informed or freely given) — the two stay two separate controls, one required, one not, so a user can see plainly that they're different kinds of decisions. Copy, first draft: *"Use my activity to power personalized suggestions for me (optional — off unless you turn it on, and you can change this anytime in Account Settings)."* Unchecked by default, exactly one click to enable, no second screen, no separate confirmation step, no re-authentication — this is what "super easy" means concretely: saying yes costs the user nothing beyond a single click inside a flow they're already completing anyway.
- **The same control, same copy, lives in Account Settings too — not just at signup.** `decisions/0010` calls this an "explicit, accessible" control; accessible means findable and changeable after the fact, not just offered once during a flow the user may not have been paying full attention to. A user who skips it at registration can turn it on later in exactly as many clicks; a user who enables it at signup can turn it off just as easily.
- **One thing worth deciding, flagged rather than assumed: whether asking at registration is actually the right *only* moment to ask.** The Personalized Insight & Productivity Engine itself is still Tier 3 — not designed, not built. Asking a brand-new user to opt into something with no concrete shape yet ("personalized suggestions" with no example of what one looks like) is a weaker, more abstract form of consent than asking once the feature actually exists and can be shown, not just described — and it's also likely to convert worse, precisely because there's nothing tangible to say yes to yet. **Recommended, not yet built:** capture the flag at registration as designed above (so the schema and default are correct from day one, per the pre-work item), but also re-surface the same one-click toggle contextually once the Insight Engine actually ships — a one-time, concrete "here's what this does now, want to turn it on?" moment for anyone who hasn't already opted in — rather than treating the registration-time answer as the only chance a user ever gets to decide. This keeps the "super easy" registration-time toggle intact while giving the eventual real decision a fair, informed moment too.

## Consequences

`Auth::attemptLogin()`'s new unverified-email rejection is a real behavior change for any account that has never confirmed its email — worth a one-time check before this ships so an already-registered account (the live export currently has exactly one `users` row) isn't retroactively locked out by a policy that didn't exist when it registered.

The `users.role` default-to-`business_owner` gap that `Auth::register()`'s own comments flagged is now resolved: registration stays a single generic flow with no resident/business branch at signup (per direction), but every account now gets a correctly-labeled `user` default instead of `business_owner`. This is a schema migration (`ALTER TABLE users MODIFY role ENUM('user','business_owner','admin') NOT NULL DEFAULT 'user'`) plus a one-line change to `Auth::register()`'s INSERT — worth doing at the same time as the login-gate change above rather than as a separate deploy, since both touch the same registration code path. It does not change what `role` actually authorizes: that remains orthogonal to the live `listing_access`/`admin_access` grants (`architecture.md` §9/§11), which is where real authorization runs today regardless of this column's value.

The registration page's Terms/consent copy — what the ToS/Privacy Policy actually say — is out of scope here. This ADR specifies only that acceptance is captured and required, not the legal content being accepted.

The new `ai_personalization_opt_in`/`ai_personalization_opt_in_at` columns are a small, additive migration alongside the `role` default change above — both touch `Auth::register()`'s INSERT and can ship in the same deploy. The exact registration-form copy above is a first draft, same status as the ToS copy note: this ADR specifies the mechanism and the default, not final legal/marketing wording. Account Settings needs the matching toggle built at the same time the registration-form one is, not as separate follow-up work, since `decisions/0010` treats "accessible" as covering both.
