# ADR 0036: Explicit Location Group Linking — Strategic/Cornerstone-Gated, Not Inferred From Shared `listing_access`

**Status:** Accepted (2026-09-25)

## Context

`decisions/0032` gated multi-location inventory management to Strategic/Cornerstone, originally scoped to "active/current listings within a user's actual `listing_access` grants (a 'user nexus')." Per direction, that scoping needs a correction before it's buildable: holding `listing_access` grants across several listings does not mean those listings are the same business, and should never be treated as one combined inventory or communications surface by default. A manager, agency, or multi-client account can legitimately hold `listing_access` on several completely unrelated businesses' listings — pooling their searchable inventory or their communications just because one account can reach all of them would be a real correctness and privacy failure, not a convenience. Per direction: "listings will not always be the same business."

## Decision

**Every listing is independent by default, regardless of who holds `listing_access` on it.** A listing's inventory, catalog cap (`decisions/0032`), and communications routing are scoped to that listing alone unless explicitly linked to others. Shared `listing_access` across multiple listings is never, by itself, a signal that those listings should be searchable, managed, or communicated with as one combined entity.

**Only the owner, or a single owner-designated Executive-level manager, can create a Location Group — corrected per direction 2026-09-25 from an earlier "any manager" framing.** The owner always retains this authority. The owner may additionally designate exactly one manager as Executive, explicitly authorizing that one person to also link listings — a deliberate, owner-granted elevation, never automatic to every manager and never self-assigned. **No further delegation past this one level, per direction:** an Executive-level manager cannot designate another Executive and cannot pass linking authority to anyone else — the chain stops at owner → one Executive, never a cascading hierarchy. Full reasoning and the same rule's application to role-creation authority is `decisions/0037` — this ADR just states the rule as it applies to linking specifically. **Each listing being linked must individually hold its own Strategic or Cornerstone subscription, per direction 2026-09-25** — Location Group eligibility is evaluated per listing (`decisions/0035`'s per-listing Subscription model), not inherited from one account-wide subscription; a listing without its own qualifying Subscription can't be added to a group regardless of who's asking. **Consistency correction, 2026-09-25:** an earlier pass of this ADR named "Cornerstone" specifically here, narrowed by SJ Portables' own Cornerstone case — corrected to match the actual multi-location gate `decisions/0032` and `commercial.md` §10 already set (Strategic/Cornerstone, Core excluded), not a stricter Cornerstone-only bar for linking itself. A Location Group is what actually enables a combined/cross-location searchable inventory view and cross-location visibility in a shared admin view. **Linking has no effect on catalog capacity, per direction 2026-09-25** — each listing keeps its own independent 250-item cap (`decisions/0032`) whether linked or not; an earlier version of this ADR also had linking enable a shared combined cap, which is removed. Grouping is purely about shared searchability and communications/admin oversight, not a pooled inventory ceiling.

**Communications route to a specific email or an assigned listing manager per listing, per direction — even inside a linked Location Group.** Linking locations together for shared inventory/admin visibility does not collapse their communications into one inbox by default. Each listing keeps its own assigned recipient (a specific email address or an assigned listing manager); a Location Group's shared admin view is a read/manage surface over those individually-routed threads, not a replacement for per-listing routing.

**Staff assignment is `listing_access` itself, per direction — not a separate staff/role system.** Whoever holds an owner/manager `listing_access` grant on a given listing is that listing's assigned recipient by default. There is no additional staff-login concept to design on top of the access grants `decisions/0002` already governs — the question of "who logs in for this location" and "who does this location notify" are the same question, answered by the same table.

**Notification channel, per direction 2026-09-25: in-app plus opt-in email.** In-app notification is the default and always on. A listing's assigned recipient can additionally opt in to email by entering an email address; once opted in, the platform sends notifications via SMTP from the server, and each email links back to the specific item or thread in the Communications Center — a real deep link into the notification, not a bare "you have a new message" alert.

## Consequences

`decisions/0032`'s original "user nexus" scoping language is superseded by this ADR's Location Group mechanism — the multi-location gate still requires Strategic/Cornerstone (unchanged), but the actual scoping mechanism is this explicit link, not inferred `listing_access` overlap. This needs its own schema shape — a `location_groups` table or equivalent linking specific `entity_id`s together, distinct from `listing_access` itself, and a per-listing routing field (assigned email or listing manager) — not yet designed, flagged here rather than assumed. SJ Portables' three locations, being a genuine single multi-location business, need this explicit Location Group created as part of their build, with their per-listing communications routing configured — neither is inferred automatically from the fact that one account manages all three. Because linking carries no combined cap, three listings that each independently grew to their own 250-item ceiling before ever being linked can be linked together with no conflict — the group cap's removal makes the over-cap-at-link-time question moot rather than needing its own resolution.
