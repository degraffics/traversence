## Purpose & Governance Role

This document is the bridge between the Charter's philosophy and technical execution. It defines how the architecture enables the platform's core mandate — replacing political borders with living connection points where information organizes organically through natural association — while maintaining network integrity across the ecosystem.

## 1. Platform Architecture State Model

Three strict operational tiers separate server reality from active work from future scope:

- **Tier 1 — As-Built:** verified, currently deployed infrastructure, database drivers, and auth backend.
- **Tier 2 — Active Development:** the current sprint — framework routing, search/CMS mechanics, portal interfaces, the communications/feed pipeline.
- **Tier 3 — To-Be-Developed:** deferred informational pages, e-commerce/pricing subscriptions, automated booking/webhook integrations.

(Feature-level detail for each tier lives in `prd.md`, organized by what the user sees rather than how it's built.)

## 2. Core Platform & Infrastructure (`/api/`) — Tier 1

- `api/bootstrap.php` — system initialization, environment loading, session params, global `ROOT_PATH` resolution.
- `api/Database.php` — core PDO database drivers and connection handlers.
- `api/ingest.php` — offsite crawler ingestion and Tier 4 quarantine engine.
- `api/auth/` — asynchronous JSON/PHP handlers: login, register, logout, verify-email, change-password, session, plus email/password recovery lifecycle.
- `api/middleware/` — CSRF (`Response::requireCsrf()`), auth guards (`require_auth.php`, `require_admin.php`). Real, live listing-scoped authorization is a per-request `listing_access` check (§9, §11, §13), not a standing session-wide role-toggle.
- `api/lib/` — shared utilities: `Auth.php`, `Mailer.php`, `TrustScore.php`, `Response.php`, `StepUpAuth.php`, `Verification.php`, `CrawlerIngest.php`, `PlaceScope.php`, `SearchText.php`, `synonyms.php`.
- Core API services: `directory.php`, `search_listings.php`, `nearby_hubs.php`, `set-home-location.php`, `places.php`, `place.php`, `suggest.php`, `categories.php`, spatial data references.
- Environment configuration & diagnostics: `.env` (DB credentials, BlueHost SMTP params) and ephemeral diagnostic scripts (`session-debug.php`). **These, along with any file carrying credentials, should be tracked in `apdex.md`'s security-flag convention, not restated here.**

**Session & security bootstrap (`api/bootstrap.php`):** native PHP sessions with secure cookies (`HttpOnly`, `SameSite=Lax`, HTTPS-aware), issuing a per-session CSRF token. State-changing endpoints under `api/auth/*` require a matching `X-CSRF-Token` header, verified via `Response::requireCsrf()`. Backend stack is plain PHP 8+ with native PDO and prepared statements exclusively, against MySQL/MariaDB today — a fact worth keeping in view against `decisions/0004-infra-migration-bluehost-to-supabase-railway.md`, which proposes moving to Postgres. Module entry points are domain-isolated (`/user/dashboard.php`, `/listing/businessportal.php`, `/admin/adminportal.php`) rather than root-level stubs.

## 3. Public Entrypoints & Auth Views

Root entrypoints, auth views, and every route's live/scoped/planned status are maintained in `routes.md` — that file is the single source of truth for URLs and page status; it isn't duplicated here.

## 4. Dual Search Engines & CMS Modules — Tier 2

Front-end discovery is driven by a dual search architecture governed by the Chameleon Filter (routing by Utility vs. Experience intent). See `decisions/0003-chameleon-filter-routing.md` for why this split exists.

- `/discovery/` (Top-Down / "Let's Explore") — corridor-based navigation, the Traveler authority engine, curated taxonomy queries against micro-clusters, dynamic content via `/discovery/api/`. Internally called the Linear Corridor Loop / Chameleon Pivot method.
- `/directory/` (Bottom-Up / "Get Local") — spatial radius search, ZIP-coordinate resolution, local utility filters, business listing discovery via `/directory/api/`.

**Search implementation details:** `api/lib/SearchText.php` normalizes, tokenizes, and ranks queries against entity titles, descriptions, and category metadata. `api/lib/synonyms.php` maps colloquial search terms to canonical category/entity slugs. Search tokens of 3 characters or fewer are forced to whole-match, high-precision lookups to suppress false-positive ranking inflation. Category filter counts are computed dynamically against the active search context and geographic boundaries, not cached.

**Geospatial handling:** listings use ZIP-centroid coordinates when exact street-level coordinates aren't available. The map pin renderer applies deterministic fanning to prevent marker collision at a shared centroid, paired with an explicit UI disclaimer: *"Pin marks the ZIP-code area, not the street address."* A future iteration is expected to integrate the US Census batch geocoder with precision flags distinguishing exact from ZIP-centroid coordinates.

## 5. Visitor Telemetry, Communications Center, & Social Feeds — Tier 2

- **Visitor telemetry:** radius queries, corridor navigation, profile views, map clicks, and inquiry taps log usage metrics for both listing operators and system administrators. Every logged event carries both dual-accounting fields (`actor_user_id`, `acting_as_listing_id`) through to storage — see `decisions/0008-activity-data-preserves-dual-attribution.md` for why this can't collapse to a single identity downstream.
- **Centralized Communications Center:** unified messaging between visitors, registered users, and listing operators, routed into `/user/`, `/listing/`, `/admin/` dashboards.
- **User Profile Feed & Connection Mechanics:** activity streams filtered by connections; the +Add/Disconnect protocol links users to listings or content posts. Per `decisions/0008-activity-data-preserves-dual-attribution.md`, this feed distinguishes a user's personal activity from activity they generated while acting as a business proxy — it is not one merged timeline.

## 6. Back-End Portals & Management Modules — Tier 2 & 3

- `/user/` — dashboard, profile management, comms inbox, activity feed, `/user/api/` endpoints. *(Tier 2)*
- `/listing/` — business portal, referral views, `/listing/api/` (claims, hours, attributes, verification tiers, vouchers, inbound comms). *(Tier 2)*
- `/admin/` — admin portal and privileged moderation endpoints under `/admin/api/`. *(Tier 2 scaffolding, Phase 7 groundwork)*
- `/hub/` & shared partials (`/includes/`, `/js/`) — hub entrypoints and cross-page layout blocks (`brand.php`, `footer.php`, `header.php`, `auth-nav.php`, `location-modal.php`, `page-shell.php`, `routes.php`).

## 7. User Account Model & Dual-Accounting Infrastructure

The Dual-Accounting Foundation (UserId + ListingId) stamps both identities on every post, comment, review, and edit via composite foreign key constraints, eliminating anonymous bias, sock-puppeting, and pay-to-play manipulation. See `decisions/0002-dual-accounting-model.md` for the full rationale and the concrete table design.

- **Trust-Weighted Interaction Mechanics** (`api/lib/TrustScore.php`) — internal trust scoring evaluates interactions, verifications, and historical consistency, so that visibility and prominence across the Resident, Traveler, and Community tracks are earned through authentic community resonance rather than artificial inflation or paid placement. Scoring must be able to segment by personal vs. business-proxy activity, not just total volume — see `decisions/0008-activity-data-preserves-dual-attribution.md`.
- **Transparent authorship via profile, not raw ID** — public-facing content (comments, reviews, contributions) is attributed to a user's front-end profile (§6), never to the raw `actor_user_id`, which stays a strictly internal accounting mechanism (trust scoring, dispute resolution, moderation). Profiles are discoverable by other users by design. Harassment/retaliation risk is handled through user-side control — block, filter, or report/request-removal of unwanted engagement — rather than by hiding identity, since concealment would undercut the accountability the trust model depends on. AI-generation systems (§23, §26) de-identify a contribution by default; identity travels with it only when a system would actually credit or key off *who* contributed it, in which case the user gets an explicit opt-out. See `decisions/0010-identity-exposure-and-ai-consent.md` (Accepted; one default-state parameter still open).

**Resolved (2026-09-22):** paid tiers (`commercial.md` §1) sell AI-content-generation access and group-management support, never ranking. This mechanism stays the sole determinant of visibility and prominence for every partner, paid or free. See `decisions/0007-paid-tiers-sell-tools-not-placement.md`.

- **Role-Toggle Header Middleware** — a persistent client-side switcher alters avatar badges and publishing permissions, passing context through session-context middleware for server-side enforcement.
- **Guest boundaries** — anonymous visitors get zero-ad, read-only access to macro-scope communities and resource hubs; all writes to the live graph require authentication. Guests may still submit limited content (corrections, comments, contribute-mode entries), but it is captured under a session-scoped `guest_session_id` — never `actor_user_id` — and held in the Tier 4 quarantine queue for admin approval (the technical content-review role, §11 — distinct from the community Steward role) before it ever reaches live data. See `decisions/0009-guest-activity-attribution-and-pattern-detection.md`.
- **Autonomous seeding & AI copilot guardrails** — external scrapers and internal workers ingest and vectorize under strict Human-in-the-Loop constraints. See `decisions/0005-hitl-ai-guardrails.md`.

## 9. Database Architecture: the Graph-in-SQL Model (Confirmed Against Live Code)

This section originally reconciled three conflicting document-only drafts of the `entities` table via `decisions/0012-unified-entities-schema-hybrid-graph-mirror.md`, including a shared-primary-key design between `entities` and `users`. A full working export of the live codebase (2026-09-23) showed that design doesn't match reality, and ADR 0012 has been revised accordingly — this section now restates the real, confirmed schema rather than the earlier synthesis.

**`entities` / `entity_metadata` / `connections` is real and live**, not just a design — 4,376 entity rows migrated from the legacy flat schema, in production today. **`entities` and `users` are independent ID spaces — no shared primary key.** `entities.owner_user_id` (nullable) is a plain foreign key, currently the MVP single-owner link; there is no `FOREIGN KEY (id) REFERENCES entities(id)` anywhere in the real schema, and there shouldn't be — a real unclaimed merchant entity exists with no user attached at all. There is no separate `business_listings` table; a listing's tier/verification state lives directly on `entities`.

```sql
CREATE TABLE entities (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    entity_type VARCHAR(50) NOT NULL DEFAULT 'merchant',  -- 'merchant' in all live data today; 'topic'/'content_asset' spec'd for §26, not yet used
    name VARCHAR(255) NOT NULL,
    status ENUM('unclaimed','claimed-unverified','pending-verification','verified',
                'disputed','pending-opt-out','opted-out') NOT NULL DEFAULT 'unclaimed',
    verified_tier TINYINT NULL,            -- 1-4, which verification route granted 'verified' — see below
    is_suppressed BOOLEAN NOT NULL DEFAULT FALSE,
    owner_user_id INT UNSIGNED NULL,       -- legacy MVP link, mid-migration to listing_access — see §11
    primary_zip VARCHAR(10) NULL,          -- geo anchor for routing / Single Home Rule, §22
    micro_cluster_id INT UNSIGNED NULL,    -- geo hierarchy placement, §22
    category_id INT UNSIGNED NULL,         -- FK to the real `categories` table — 23 groups / 818 leaves, see §18
    latitude DECIMAL(10, 8) NULL,
    longitude DECIMAL(11, 8) NULL,
    composite_hash CHAR(64) NULL,          -- SHA256(lowercase(trim(name)+trim(address)+trim(zip))) — claim-aware match key, ADR 0012
    trust_score DECIMAL(8,2) NOT NULL DEFAULT 10.00,
    created_by_type ENUM('ai_crawler','user','owner','admin') NOT NULL DEFAULT 'ai_crawler',
    updated_by_type ENUM('ai_crawler','user','owner','admin') NOT NULL DEFAULT 'ai_crawler',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NULL,
    FOREIGN KEY (owner_user_id) REFERENCES users(id) ON DELETE SET NULL,
    FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE SET NULL
);

-- Flexible, type-varying attributes only (hours, media URLs) — not a catch-all.
-- Field-level lock: once a human (owner/admin/high-trust user) edits a field, it's
-- locked against future automated overwrites, independent of any record-level status.
CREATE TABLE entity_metadata (
    id INT AUTO_INCREMENT PRIMARY KEY,
    entity_id BIGINT UNSIGNED NOT NULL,
    meta_key VARCHAR(100) NOT NULL,
    meta_value TEXT NOT NULL,
    source_type ENUM('ai_crawler','user','owner','admin') NOT NULL DEFAULT 'ai_crawler',
    trust_score DECIMAL(8,2) NOT NULL DEFAULT 10.00,
    is_locked BOOLEAN NOT NULL DEFAULT FALSE,
    FOREIGN KEY (entity_id) REFERENCES entities(id) ON DELETE CASCADE
);

-- Edges. relationship_type in live use today: 'VERIFIED_BY' (Peer Validation, §25).
CREATE TABLE connections (
    id INT AUTO_INCREMENT PRIMARY KEY,
    source_id BIGINT UNSIGNED NOT NULL,
    target_id BIGINT UNSIGNED NOT NULL,
    relationship_type VARCHAR(100) NOT NULL,
    created_by_type ENUM('ai_crawler','user','owner','admin') NOT NULL DEFAULT 'user',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (source_id) REFERENCES entities(id) ON DELETE CASCADE,
    FOREIGN KEY (target_id) REFERENCES entities(id) ON DELETE CASCADE
);

-- users: fully independent of entities. No Auth0 anywhere — see §11.
CREATE TABLE users (
    id INT(10) UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    display_name VARCHAR(255) NULL,
    role ENUM('user','business_owner','admin') NOT NULL DEFAULT 'user',  -- 'user' added 2026-09-23 (decisions/0014) to close the "every registrant defaults to business_owner" gap; 'business_owner'/'admin' values are legacy, mid-migration — see §11
    is_admin BOOLEAN NOT NULL DEFAULT FALSE,                                 -- legacy, mid-migration — see §11
    trust_score DECIMAL(8,2) NOT NULL DEFAULT 0.00,
    session_version INT NOT NULL DEFAULT 1,        -- bump to invalidate every other active session
    is_suspended BOOLEAN NOT NULL DEFAULT FALSE,
    email_verified_at TIMESTAMP NULL,
    home_cluster_id INT UNSIGNED NULL,      -- secondary/derived location field, see §23
    area_zip VARCHAR(10) NULL,              -- primary location-resolution fields, see §23
    area_city VARCHAR(100) NULL,
    area_state VARCHAR(2) NULL,
    area_lat DECIMAL(10,8) NULL,
    area_lon DECIMAL(11,8) NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NULL
);
```

**Ownership and admin access are real, live capability grants — see §11** for `listing_access`/`admin_access`, the two tables that are actually authoritative here (not `listing_ownership`, not an `OWNER_OF` connections edge — neither exists in the real system).

**`composite_hash`'s confirmed purpose and exact formula: `SHA256(lowercase(trim(name) + trim(address) + trim(zip)))`, for claim-aware scraper matching and field-level overwrite protection.** A re-scrape hash-matches an entity that already exists — including one already claimed and verified — rather than creating a duplicate. Protection is enforced per-field via `is_locked` on `entities`/`entity_metadata`, not as a blanket "route the whole record to HITL" rule: a claimed, verified listing can still legitimately absorb new data on fields nobody has touched yet, while any field a human has directly edited is permanently immune to a later scrape regardless of recency. See §25 for the full ingestion-pipeline mechanics and `decisions/0012` for the full decision record.

**Verification — four independent tiers, real and live (this replaces any earlier speculative claim-aware-matching-only description of how a listing reaches `verified`).** A listing moves through `unclaimed → claimed-unverified → pending-verification → verified`, plus `disputed` and the opt-out branch (`pending-opt-out → opted-out`) — the enum on `entities.status` above. Claiming itself (`/claim`, real and live: two-step, OTP to the claimant's own account email, then `owner_user_id` is set) is frictionless and doesn't verify anything by itself. From `claimed-unverified`, any one of four independent routes grants `verified` — none is a prerequisite for another, and there is no aggregate point threshold across them:

| Tier | Route | Mechanism | Entity bonus | User bonus |
|---|---|---|---|---|
| 1 | Self-Confirm | A dedicated, owner-triggered OTP challenge, separate from the claim OTP — proves the account holder is real and reachable, not that they're connected to the business (lowest tier, lowest bonus) | +20 | +10 |
| 2 | Referrals | Claimant names up to 3 registered users; each must actively click their own confirmation link. 3 confirmed referrals grants Verified **and** auto-flags the entity for retroactive admin review (non-blocking) | +30 | +12 |
| 3 | Peer Validation (vouchers) | 3 confirmed `VERIFIED_BY` connections edges from entities that are themselves already Verified at Tier 2+ (a Tier-1-only entity cannot vouch, to stop Tier 1 laundering into Peer Validation) | +35 | +15 |
| 4 | Admin Override | Direct manual decision — the apex authority for anything escalated, disputed, or ambiguous | +50 | +25 |

Supplemental, stackable bonuses on top of whichever tier applied: +10 entity/+5 user for a business document on file; +2 entity for each referral/voucher beyond the minimum 3 (capped at 3 extra). `entities.verified_tier` records which route was used. Trust score reflects *how* a listing got verified; it is never a second, independent gate to verification itself. Real schema: `entity_referrals` (`entity_id`, `referrer_user_id`, `confirmation_token`, `confirmed_at`), `verification_attempts` (audit/review log, including Tier 2's auto-flagged retroactive-review rows), `user_otp_challenges` (the shared `StepUpAuth` OTP table — see §11). All four tiers, the trust-score economy, and the OTP infrastructure are built and live; only the admin-facing review queue that Tier 2's flagged entries and Tier 4 depend on (Phase 7 admin panel) is not yet built.

**Claim/verification flow fleshed out 2026-09-23 (`decisions/0015-claim-verification-flow-and-dispute-resolution.md`).** The tiers above were always real, but had no working front door: `/claim` was an explicitly-labeled disabled mock, Tier 2's referral-naming and Tier 3's vouch-selection had no UI at all (the dashboard only ever *displayed* progress toward them), and `listing/confirm-referral.php` called a `POST /listing/api/referral/confirm.php` contract that didn't exist — the same "real front end, missing backend" gap `decisions/0014` found in registration. `decisions/0015` wires all of that up, adds the `api/referral/create.php`/`confirm.php` pair, and makes claiming write a real `listing_access` (`owner`) row alongside the legacy `owner_user_id` column it already sets (closing one more piece of `decisions/0012`'s migration gap). It also builds the previously entirely-unbuilt dispute/challenge flow: `entities.status`'s existing `disputed` value gets a real write path via the `disputes` table, resolving to the claimant re-verifying at Tier 3+, an admin revoking the claim (back to `unclaimed`, never auto-granted to the disputer), or another admin resolution. **Display during a dispute, revised same day, per direction:** the first pass reused `api/search_listings.php`'s existing `PUBLIC_STATUSES` whitelist as-is, which excludes `disputed` entirely — meaning one filing, unreviewed, could disappear a business from search. That's since been changed: `disputed` is now included in `PUBLIC_STATUSES`, but rendered at the same limited display an unclaimed listing already gets (no claimed/verified badges, no owner-supplied description/photos, no paid-tier perks — baseline crawler fields only, computed fresh from `status` with no separate flag to track) and deliberately no public "disputed" label. The listing never disappears; it just loses its claimed polish until the dispute resolves. **Precursor check on triggering that, revised again same day, per direction:** even limited display is a real cost, so filing alone doesn't auto-flip `status` anymore — the filer must clear a standing check first (account `trust_score >= 0` and email-confirmed 72+ hours, or a domain-email OTP match when the entity happens to have a `website` on file) or the dispute still gets logged but sits in `admin/claims.php`'s queue for a human first look before anything about the listing changes. **A two-tier clock, added 2026-09-24 per direction so the process stays fast and efficient rather than just eventually resolving:** the moment `entities.status` actually flips to `disputed`, two deadlines start on the `disputes` row — `challenge_deadline` (7 days, the hard outer ceiling) and a new `response_deadline` (48 hours, a first-response window nested inside it). The claimant has to actually respond — re-verify at Tier 3+, or submit a document (`decisions/0017`) — not just wait out the week. An admin's "Request more info" action resets the 48-hour clock, capped so it can never push past the 7-day ceiling. **Editing freeze, reversed the same day per direct correction:** a dispute now genuinely freezes the claimant's ability to edit listing content (description, photos, `entity_metadata`) for as long as `status = 'disputed'`, on top of the already-limited public display — reasoning being that frictionless, unverified claiming (above) shouldn't also come with unrestricted editing rights during an active challenge. The specific defense actions (Tier 1/3 re-verification, document upload) stay explicitly exempt from the freeze, or there'd be no way to actually respond to a dispute. The freeze lifts on any of three paths: the defense validates (`claimant_reverified`), an admin dismisses, or — the one deliberate, narrow exception to this platform's otherwise-uniform HITL rule — the claimant stays silent past the 48-hour `response_deadline`, which auto-resolves the case as a new `claim_abandoned` state (reverts to real `unclaimed`, no trust penalty, no admin click required). The punitive outcome (`claim_revoked`, with a trust penalty) stays fully human-gated, unchanged. Worth knowing regardless of this ADR: domain-email verification was already tried once on this platform, for Tier 1, and explicitly dropped as "chasing our tail" once real usage showed many businesses don't maintain a separate domain — the real database export confirms this empirically (`website` populated on none of the sampled entities, versus `phone` on 63 of 70) — so domain-match here is an opportunistic accelerant, not the default gate. A claimant-facing "request manual review" intake for Tier 4 is added too, queuing into the same `verification_attempts` pending-review surface Tier 2's auto-flagging already uses. **The reviewing side is now real too (`decisions/0016`, same day):** `admin/claims.php` — the "Claims" tile `admin/adminportal.php` already names but leaves unbuilt — is a hub-scoped queue over exactly that pending surface. A Tier 4 intake row approves into a real `Verification::applyAdminVerification()` call; a Tier 2 retroactive-audit row, since its entity is already live and verified, doesn't get instantly revoked on one admin's flag — flagging it opens a real dispute (§14, `decisions/0015`) instead, so a live listing never loses its verification without the same challenge-and-respond window a peer-filed dispute gets — and, per the display revision above, never loses its search presence either, only its polish. A third row type — a dispute whose filer never cleared the precursor check above — sits here too, untouched until an admin decides whether to escalate it (which is what actually flips `status = 'disputed'`) or dismiss it outright. **Manual phone verification, added same day (`decisions/0016`):** rather than leaving the phone-based fast path flagged as future work blocked on SMS/telephony infrastructure, any admin reviewing a Tier 4 intake row or an unproven-dispute row in `admin/claims.php` now gets a "Called listed number" field (`phone_verified: true|false|null`, plus a note) on the same decision — the call happens, it's just placed by the admin rather than an automated provider. No schema change: it's recorded in the free-text `notes` the approval/resolution already writes. Framed explicitly as the interim form of the stronger, eventually-desired automated version — real listings have `phone` populated far more often than `website` (63 of 70 sampled vs. 0) — it ships now because it costs no new infrastructure, only admin time. **Document upload, added `decisions/0017`, revised the next day per direction:** the platform's first real file-upload feature. A claimant filing a Tier 4 intake request, or a user filing a dispute, can now attach a supporting document (utility bill, business license, etc.) via `POST /api/documents/upload.php`, stored in a new `verification_documents` table pointing at a file kept outside the webroot (`/storage/verification-documents/`), never served by a public URL. `admin/claims.php` shows a document indicator per row and reads the file back only through a hub-scoped, admin-gated `admin/api/documents/view.php`, the same `Auth::requireHubAdmin()`/`requireSuperAdmin()` check every other action in `decisions/0016` already uses. The old advice to email documents to a monitored admin address stays as a fallback, not the default. **Documents are purged 72 hours after the case they're attached to resolves** — a home address or account number on a submitted document no longer sits on disk indefinitely, resolving what the original ADR had only flagged. **Images are compressed on upload** via PHP's built-in GD library (resized, re-encoded, which also strips EXIF metadata as a side effect — a second privacy win); PDFs aren't, since real PDF compression needs an external tool this hosting setup isn't confirmed to allow. **An automated pre-screening pass** checks the file is actually readable (hard-fails at upload, before any queue row exists, with an immediate reason to the uploader — this part stays synchronous on Bluehost) and, for readable files, runs OCR against the document. **Revised twice more the next day, per direction:** first to structure the OCR read using `decisions/0011`'s existing Who/What/Where/When/Why classification approach rather than free-text reasoning — What (document type), Where (address found), When (document date), Why (the stated match reasoning), and Who adapted to mean the business/entity the document is claimed to support (a different, already-public kind of identity than the system-user identity `decisions/0011` was walling that key off from) — with only this five-key classification ever stored, never the raw OCR'd text. **Then, once a real hosting constraint came to light: OCR moves off Bluehost entirely.** Bluehost hard-blocks `shell_exec()`/`exec()` account-wide via `disable_functions`, and would throttle-kill a CPU-heavy binary process even if it didn't — so OCR now runs as an async job on a Railway worker (`decisions/0004`'s deferred async layer, now actually triggered), which fetches the file through a shared-secret-authenticated internal endpoint and writes back only the five-key classification. This also changes what "eliminate manual review" means in practice: a `review_status` of `auto_confirmed` (a recognized document type plus a clear name/address match — a conservative bar) lets an admin act without personally opening the file; anything less confident is `needs_review` and still requires that manual look. **What never changes: the case decision itself.** `decisions/0016`'s decide endpoint has always required a human admin's own action — Accept, Override (either direction), Request more info, or Deny — and nothing here creates a path around that; only the redundant step of re-checking a confidently-matched document is what's actually eliminated. See `decisions/0015`'s Consequences section for what's still a first default rather than a researched threshold (the 7-day challenge window itself, and whether limited display alone sufficiently deters pure harassment filing).

## 10. Master Engineering Blueprint & Execution Architecture

- **Locked stack conventions:** front-controller pattern with a lightweight custom router, native PHP 8+ PDO, explicit composite indexing for spatial/filter fields, route namespace isolation (`/listing/`), hierarchical canonical URLs (`/[macro-hub]/[geo-hub]/cluster-[id]`).
- **Master platform inventory:** taxonomy structure (Macro Hub → Geo-Hub → Micro-Cluster), core `/api/` endpoints, public gateways, management portals.
- **Integrated production modules:** Stripe checkout, media asset management, transactional email (`Mailer.php`), automated logging.
- **The 6-step build order:**
  1. Foundation — bootstrap, DB drivers, router, auth guards.
  2. Core Data & Hierarchy — entity schema, migrations, CRUD interfaces.
  3. First Vertical Slice — trust loop, claim flow, verification queue.
  4. Discovery Engine — public search, `/directory`, `/discovery` (§19, ADR 0013 — real, live route names; `/get-local`/`/explore` were never built under those names), map, Chameleon Filter.
  5. Content & Monetization — editorial templates, shortcode injection, Stripe hooks.
  6. CrawlerIngest Subsystem — automated parsing and staging.

## 11. System Security & Identity Enforcement

**Actors:**

- **Guest visitor** — unauthenticated, temporary guest-tier token, read-only against live data, zero credibility; inputs are captured under a `guest_session_id` and subject to immediate admin curation and purge, never a direct live write. Cross-session correlation (cookie primary, IP-based clustering fallback) feeds a separate guest risk score for abuse-pattern detection, purpose-limited to source attribution, conflict resolution, and abuse detection — see `decisions/0009-guest-activity-attribution-and-pattern-detection.md`.
- **Personal human user** — authenticated via the real, live custom auth system (native PHP sessions, no Auth0 — see Mechanism below); unlocks an ad-free dashboard, saved places, community chat. Publicly represented by a front-end profile, not the raw ID — see the Trust-Weighted/transparent-authorship bullet in §7 and `decisions/0010-identity-exposure-and-ai-consent.md`.
- **Verified local business — owner/manager, via `listing_access`** — a listing is claimed via `/claim` (real, live: two-step OTP to the claimant's own account email, then `entities.owner_user_id` is set — see §9 for the full four-tier verification path to `status = 'verified'`). **Claiming proves the claimant controls an email account, not that they're associated with the business — confirmed as a deliberate, platform-wide "frictionless first, correct after" pattern (the master spec's own words), not a gap.** The real assurance is downstream: a visibly distinct `claimed-unverified` status, the four verification tiers, and the dispute mechanism (§9, `decisions/0015`) as the actual backstop against a wrong claim. Real, live ownership is a capability grant, not a single-owner flag: `listing_access` (`entity_id`, `user_id`, `access_level` ENUM `owner`/`manager`, `granted_by_user_id`) lets more than one user be attached to a listing — `owner` has full authority (edit, transfer, invite/remove managers); `manager` has day-to-day authority only. `entities.owner_user_id` is the legacy MVP link, still live, mid-migration to being fully superseded by `listing_access` (add-then-migrate-then-drop, not yet dropped). **As of `decisions/0015` (2026-09-23), the claim flow writes both**: `/claim`'s confirm step now inserts the claimant's own `listing_access` (`owner`) row in the same transaction as the `owner_user_id` write, so ownership stops being created into only the column that's supposed to be phased out — claims made before this change still need a separate backfill pass into `listing_access`. **`manager` rows are now real too (`decisions/0018`, 2026-09-24):** an owner can invite a colleague (registered, email-confirmed, confirmation-gated — the same guest-exclusion boundary as everything else on this platform) via `listing/api/managers/invite.php`; Tier 1 self-confirm, Tier 3 vouching, and Tier 4 intake all check owner-or-manager access now, while inviting/removing managers and transferring ownership stay owner-only. **`decisions/0018`'s own flagged gaps — a manager cap, and a "promote a manager to owner" transfer flow — are now closed, 2026-09-25 (`decisions/0038`):** the owner can never be removed, only transferred to another active/registered user who must explicitly accept (mirroring this same invite/accept pattern), with financial responsibility (the per-listing Subscription, `decisions/0035`) transferring alongside it, and a real keep/remove choice over existing delegates offered independently to both the outgoing and incoming owner. **`listing_access` also grows two more extensions this same day, layered on top of owner/manager rather than replacing it:** an owner may designate exactly one manager as **Executive**, an owner-granted elevation authorizing that one person (and only that one, with no further delegation past it) to also create a **Location Group** — an explicit, deliberate link between listings for shared searchability/admin visibility, never inferred from one user simply holding `listing_access` across several listings, which may not even be the same business (`decisions/0036`) — or to create further delegated roles below manager, each with owner/Executive-configured capabilities rather than a fixed named role (`decisions/0037`). Schema for all three (a transfer-pending state, a `location_groups`-shape table, and an Executive/configurable-role structure) is not yet designed — flagged in each ADR, not assumed here.
- **Administrator** — the technical-pipeline role, now with real, live tiering rather than a single flat flag: `admin_access` (`user_id`, `hub_id` nullable, `tier` ENUM `super_admin`/`regional_admin`) — `regional_admin` is scoped to one hub via `hub_id`; `super_admin` has platform-wide reach via `hub_id IS NULL`. A one-time, self-service "Become Super-Admin" bootstrap grants the first platform admin (an atomic `INSERT...WHERE NOT EXISTS`, closing a race a naive count-then-insert would leave open) — real and live. Legacy `users.is_admin` remains live and load-bearing in `Auth.php`'s `requireAdmin()` today (confirmed 2026-09-23 by a direct grep of `api/`: `requireAdmin()` gates on `is_admin` alone, not `role` — `users.role` carries no live authorization weight anywhere in the codebase, only the `is_admin` flag does), not yet migrated to the new tiered helpers (`canAdministerHub()`, `requireHubAdmin()`, `isSuperAdmin()`, `requireSuperAdmin()`, `getListingPermission()`, `requireListingAccess()`, `hasAnyAdminAccess()`), which exist and work but aren't yet the only path. Administrator performs every HITL content-review sign-off referenced elsewhere in this document (`decisions/0005-hitl-ai-guardrails.md`, `decisions/0009-guest-activity-attribution-and-pattern-detection.md`, §25's article-publishing gate) — this is a system-access role, not a community one.
- **Steward** — a community-level role, not a technical one, and not global: it's held per-community, and a community can have more than one Steward at once (see §27). **Seating is assignment-based, not elected (revised 2026-09-23, per direction).** A community's creator is automatically seated as its first Steward the moment the community is created — no vote, no waiting period. Any existing Steward of that community can directly appoint additional co-Stewards at any time, the same way — a straight assignment, not a nomination-and-vote process. Election (§14's `PENDING_STEWARD_ELECTION`) is now the fallback path only: it fires solely when a community is left with zero Stewards (every Steward abandoned it and none appointed a successor first) — the normal, expected path is direct assignment by the creator or an existing Steward, start to finish. Core responsibilities are charter governance (upholding the established community rules), active management and moderation of community discussion spaces, and conflict resolution (handling group-dynamics friction, policy violations, and disputes between community members). A Steward does not review or approve scraped/AI-generated content, guest submissions, or anything else in the technical content pipeline — that is Administrator's job. Earlier drafts of `decisions/0005` and `decisions/0009` used "steward" loosely for the Administrator's technical role; those have been corrected to keep the two separate. §27 defines the per-community charter model this role governs and the Level 1/2/3 escalation ladder that routes disputes to a community's Stewards at Level 2.

**Actor Tier Reference (added 2026-09-23) — the one list, why it isn't one column.** All five tiers above are a real, useful ladder to think in — guest through Steward — but only the first two are mutually exclusive states of a single account; the rest are independently stackable grants layered on top, which is exactly why `users.role` can't be widened to hold them (see `decisions/0014`'s discussion of the same question for the `user`/`business_owner`/`admin` default):

| Tier | What it takes | Backing mechanism | Exclusive with the others? |
|---|---|---|---|
| Guest | Nothing — no account | No `users` row at all; `guest_session_id` only | Yes — a `users` row means you're at least "User" |
| User | Register + confirm email (`decisions/0014`) | `users` row, `role = 'user'` by default | No — the floor everyone else stands on |
| Listing owner/manager | A successful `/claim` | `listing_access` row(s) — per-listing, many-to-many; one user can be `owner` on one listing and `manager` on another simultaneously | No — stacks with User, Admin, and Steward |
| Administrator | Bootstrap or grant | `admin_access` row (`super_admin`/`regional_admin`, hub-scoped) — today, also legacy `users.is_admin` | No — stacks with the others |
| Steward | Create a community, or get appointed by an existing Steward | Per-community assignment (§27) — a `community_stewards`-shape join once §27's schema lands; scoped to that one community, and a community can have more than one Steward | No — held per-community, so "Steward of A" says nothing about community B |

A single global column can express "User," and — for now, as a legacy simplification — "Admin," but it structurally cannot express "owner of listing A, manager of listing B, and Steward of community C" at once, which is a completely ordinary account on this platform. That's the concrete reason the tiers below User live in grant tables, not in `role`.

**Security objectives:** absolute traceability of every write to a verified human or proxy identity; prevention of proxy spoofing and unauthenticated writes; context isolation between admin/business/personal roles; collision and edge-case protection (concurrent ownership claims, expired sessions mid-write, malformed payloads).

**Mechanism (real, confirmed — this replaces an earlier, unbuilt Auth0/TypeScript-Express description):** native PHP sessions (`api/bootstrap.php` — `HttpOnly`, `SameSite=Lax`, HTTPS-aware secure cookie, a per-session CSRF token issued to every session including anonymous ones), password hashing via `PASSWORD_ARGON2ID` with automatic `PASSWORD_BCRYPT` fallback on PHP builds without the Argon2 extension. State-changing endpoints validate `X-CSRF-Token` via `Response::requireCsrf()`. A `users.session_version` column is the session-invalidation mechanism: bumping it (on password change, or a confirmed email-revert) invalidates every other active session for that user without tracking individual session IDs. A generic **step-up OTP service** (`StepUpAuth.php`) covers claim confirmation, password-change re-verification, and email-change proof-of-destination through one shared mechanism (`purpose`: `claim` / `password_change` / `email_change` / `tier1_verify`) rather than one-off implementations per feature. For a proxy write to a listing, the live check is `Auth::requireListingAccess($entityId, $minLevel)` against `listing_access` (see the business-proxy actor above) — there is no `x-acting-as-listing-id` header or session-context role-toggle middleware in the real system; a listing-scoped action is authorized per-request against the resource being acted on, not by a standing "acting as" session mode. If a dashboard-level "switch context to acting as Business X" UX is still wanted, it would be a front-end convenience built on top of this same per-request check, not a different authorization mechanism — flagged here as a forward design note, not yet specified or built.

**Admin auth resolved as shared session, not a separate login system (`decisions/0029`, 2026-09-24) — and a real `currentUser()` gap this surfaced.** Admin status is `is_admin`/`admin_access` layered on the same `users` identity and the same `Auth::attemptLogin()` session every other login uses — never a parallel credential store. Checking the real `currentUser()` directly against that resolution surfaced a live gap worth fixing, not just noting: its SELECT never includes `is_suspended`, and its only two self-heal checks are the row being entirely missing (an actually-deleted user) and a `session_version` mismatch — so a user suspended mid-session (a rogue-admin suspension, a `decisions/0019` DMCA strike, a `decisions/0026` legal hold) keeps a fully working session, admin included, until they log out on their own or `session_version` happens to change for an unrelated reason. The function's own inline comment claims otherwise ("deleted/suspended mid-session — treat as logged out"), but the code doesn't actually check suspension. Fix: add `is_suspended` to `currentUser()`'s SELECT and treat `1` the same way the adjacent `session_version` mismatch already is — a real, live gap to close, not a hypothetical. See `decisions/0029` for the full reasoning and `admin/login.php`'s three-case behavior.

**Registration flow (fleshed out 2026-09-23, `decisions/0014-registration-flow-and-email-verification-gate.md`).** The live `register.php`/`Auth::register()` pair was a placeholder — a real account gets created (email, password, optional display name), but nothing sends a confirmation email, nothing blocks use of an unconfirmed account, and the form's own password-strength copy ("10+ characters") doesn't match what the server actually enforces (8+ characters, upper, lower, number, special character). This is fixed by wiring together three pieces that already exist rather than adding new mechanism: `Auth::register()` already issues an `email_confirmations` row (`action_type = 'registration'`); `Mailer.php` already sends authenticated mail; `verify-email.php` and `Auth::confirmEmailToken()` already exist and already agree on a `{token}` contract. Concretely: registration adds a required Terms/consent checkbox (enforced server-side, no new table — the `email_confirmations` row's own timestamp is sufficient provenance) and corrects the password-policy display to match the real rule; `POST /api/auth/register.php` now actually sends the confirmation email through `Mailer.php` after `Auth::register()` succeeds; and `Auth::attemptLogin()` gains a real behavior change — it now rejects login with a clear message when `email_verified_at IS NULL`, rather than silently succeeding and just reporting `email_verified` as a flag. No session is created at registration itself (unchanged). A resend-confirmation action (surfaced when login fails for this reason) re-issues and re-sends a fresh token via the same `issueEmailConfirmation`/`Mailer.php` path. **The `role` default gap is now closed too (2026-09-23).** `Auth::register()`'s own code comment had flagged that `users.role` had no "plain resident" value and every new account silently got the table's `business_owner` default. The fix keeps registration a single generic flow — no resident/business branch at signup, per direction — while no longer mislabeling every new signup as a business the moment they register: `role` gains a third value, `user` (`ENUM('user','business_owner','admin')`), which becomes the new column default, and `Auth::register()`'s INSERT now sets it explicitly rather than falling through to a stale default. This was pure data mislabeling, not a live authorization gap — a full grep of `api/` confirms `business_owner` was never checked as a gate anywhere in the codebase, and `requireAdmin()` gates on the `is_admin` column alone, not `role` (correcting an earlier, less precise claim in `decisions/0012` that `role` was load-bearing there). Real authorization for anything meaningful still runs through `listing_access`/`admin_access`, not `role` — this column's only live consumer today is `requireAdmin()`'s `is_admin` check, which is unaffected by this change. `business_owner` and `admin` remain in the enum as the pre-existing legacy values (still written by whatever old call sites relied on the previous default/`is_admin` pairing) until the platform's own `role`/`is_admin` → `admin_access` migration completes.

## 12. Scalable Infrastructure & Asynchronous Queues (Forward Design — Not Yet Built)

**Not confirmed against the live system.** Nothing in the real platform spec or live code describes a Redis message broker, named queues, or a Dead Letter Queue — this section should be read as forward architectural intent for when async infrastructure is actually needed, not as-built. What's real today, per §12.3 of the master platform spec: an offsite worker (a lightweight VPS, not BlueHost itself) posts lightweight, HMAC-signed REST payloads directly to a BlueHost API endpoint (`api/ingest.php`) — no message broker, no queue names, no DLQ. This is deliberate: BlueHost shared hosting can't run multi-threaded scrapers or hold long-lived worker processes, so the actual pattern is "compute offsite, POST a small payload," not "publish to a queue Bluehost itself consumes." If a real Redis/queue layer is ever built, it's likely to land alongside the Railway migration trigger already described in §16 (queue/worker layer), not before.

The four conceptual queues below remain useful as a target shape for that future layer:

- `chat-vectorization-queue` — chunks live conversation streams, generates embeddings, appends semantic knowledge nodes to the graph.
- `ingestion-scrape-queue` — pulls public utility/municipal data into a staging holding zone for HITL validation.
- `notification-auth-queue` — time-deterministic tasks: OTP dispatch, Tier 1 verification emails, security alerts.
- `maintenance-sync-queue` — scheduled cron jobs for cache flushing, index re-weighting, graph-mirror consistency audits.
- **Dead Letter Queue (DLQ):** any payload failing three consecutive times shunted with an attached trace ID.

## 13. Implementation Reference

**Listing-proxy write enforcement — real, live mechanism (this replaces an earlier placeholder describing an `x-acting-as-listing-id` header and a TypeScript/Express middleware neither of which exist in the real system).** What actually gates a write to a specific listing, per `Auth.php` and `listing/api/*`:

- `Auth::requireAuth()` verifies the session identity on every request; unauthenticated requests are rejected with a 401 before anything else runs.
- For an action scoped to a specific listing, `Auth::requireListingAccess($entityId, $minLevel = 'manager')` checks `listing_access` for a matching, sufficiently-privileged (`owner` or `manager`) grant for the current user against that `entity_id` — see §9/§11 for the real schema. There is no session-wide "acting as" mode to toggle; authorization is checked per-request against the specific resource being acted on.
- If no sufficient grant exists, the request is rejected with a clear error — there's no proxy/personal fallback to reason about, since the check is scoped to the one resource in the request, not a standing identity mode.
- `entities.owner_user_id` (legacy, still live) is what the MVP claim flow (`api/claim.php`) writes to directly; `listing_access` is backfilled from it and is the target authoritative source once the add-then-migrate-then-drop sequence (§9, ADR 0012) completes.

This lives in the real codebase today — `api/lib/Auth.php`'s `getListingPermission()`/`requireListingAccess()`, plain PDO against `listing_access` — not a placeholder awaiting translation. A dashboard-level "acting as Business X" context switch, if wanted as a UX layer on top of this, remains an open, unspecified design question (see §11's closing note), not a gap in the enforcement mechanism itself.

## 14. Edge-Case Governance & Data Lifecycle

- **Guest-to-user promotion** — session middleware re-evaluates anonymous payloads on authentication, binding recent telemetry to the new UserId. Any pending or approved contributions tied to the visitor's `guest_session_id` are re-attributed to the new `actor_user_id` at the same time. See `decisions/0009-guest-activity-attribution-and-pattern-detection.md`.
- **Role-toggle session expiration** — expired or revoked sessions mid-write drop the UI to resident mode and cache the draft locally.
- **Ownership collisions** — concurrent claims on one listing lock the entity node and flag an admin conflict. **Distinct from a post-claim dispute** (real, 2026-09-23, `decisions/0015`): a collision is two claim attempts racing at the same instant, caught by `listing/api/claim.php`'s own row lock; a dispute is someone challenging an *already-settled* claim afterward, handled by the separate `disputes` table/flow — sets `entities.status = 'disputed'` (a real, pre-existing enum value — displayed at limited, unclaimed-style visibility while disputed, never hidden from search, **and, as of 2026-09-24, with the claimant's own editing frozen too** — see §9), gives the current claimant a `challenge_deadline`/`response_deadline` pair to re-verify at Tier 3+ or submit evidence, and never auto-grants the listing to the disputer even on revocation or the new automatic `claim_abandoned` outcome.
- **Community abandonment** — **narrowed 2026-09-23 (§11, §27):** since Steward seating is now assignment-based (creator seated automatically at creation; existing Stewards appoint co-Stewards directly, no vote), abandonment by one Steward is a non-event as long as the community still has at least one other Steward — governance simply continues under whoever's left, no election involved. `PENDING_STEWARD_ELECTION` now triggers only in the genuine last-resort case: every Steward has abandoned the community and none appointed a successor first, leaving it with zero Stewards. Only then does it open a voting window for verified participants to elect a new Steward (the community-governance role defined in §11, distinct from Administrator).
- **User account deletion** — two distinct triggers into the same anonymization mechanism, per `decisions/0026-dsar-export-and-erasure-pipeline.md`: a user's own self-service deletion through the UI keeps the original 30-day undo grace period (a product kindness, not a legal requirement), while a verified DSAR/GDPR Article 17 erasure request skips that grace period and executes synchronously on verification — both anonymize contributions via the same universal `DELETED_USER_UUID` placeholder.
- **Business listing offboarding** — nodes retained permanently; ownership links flip to `ARCHIVED_CLAIM`.
- **Chat log retention** — raw chat streams purge on a 90-day rolling window once vectorized.

## 18. Taxonomy & Search Fallback Architecture

Resolves the "taxonomy concept" the Charter refers to but doesn't itself define — the mechanism lives here rather than in `charter.md`, per the no-duplication rule.

**Concentric Taxonomy Fallback:** when a query returns insufficient local results, the system automatically escalates outward through a fixed sequence: Micro-Cluster → Adjacent Cluster → Geo-Hub → Continental Hub. This is what lets a sparse rural cluster still return something useful instead of an empty page.

**Category taxonomy — real, live, two-level category system.** 24 Level-1 browse groups (drive the Directory dropdown/quick chips) and 818 Level-2 leaf categories (figure predates the group-11 addition below and hasn't been recounted against it yet), each leaf under exactly one group. `entities.category_id` (§9) points at a leaf; the original raw crawler category string is kept untouched in `entity_metadata` as provenance, not discarded. **The mechanism that prevents a second "121 in a catch-all" backlog from ever accumulating: `decisions/0024`, added 2026-09-24.** Weighted keyword dictionaries per category — now built against the real 24-group target list in `decisions/0028` rather than an undocumented placeholder — real word-boundary tokenization with stemming/stop-word filtering (the direct fix for the false-positive failure mode `decisions/0023` hit doing this by hand — "spa" inside "newspaper," "esthet" inside "anesthetist"), and a confidence threshold (>80% auto-assign, <50% routes to admin review) that pre-fills the category field an admin sees during `decisions/0005`'s already-mandatory review, rather than skipping that review. Runs inline on Bluehost — confirmed lightweight enough that it doesn't hit the `disable_functions`/resource-throttling wall `decisions/0017`'s OCR case did. This is the third instance of the same classify-with-confidence-and-fallback shape in this document set (after `decisions/0011` and `decisions/0017`), now named as a standing pattern rather than reinvented a fourth time.

**Open migration question `decisions/0028` flags rather than resolves:** the 4,376 already-migrated businesses carry `category_id` values assigned under the original, never-documented raw group structure. Adopting this refined 24-group list as canonical means those existing assignments may need re-mapping onto it during rollout, beyond just the known 121-record cleanup — not yet scoped or scheduled.

## 19. Hierarchical Slug Structure & Pilot Regional Staging

**One shared route tree, not two.** `decisions/0013-consolidated-routing-directory-discovery-entry-points.md` resolves what was previously described as two different slug patterns for the two funnels. `/directory` and `/discovery` (matching §4's Chameleon Filter naming) are the only two funnel-specific routes — the sole entry points, replacing the earlier `/get-local` and `/explore` names. Beneath them, both funnels converge on one canonical, nested, slash-delimited hierarchy:

- `/[hub-slug]` — Continental Hub landing
- `/[hub-slug]/[geohub-slug]` — Geo-Hub landing
- `/[hub-slug]/[geohub-slug]/[cluster-slug]` — Micro-Cluster landing

A visitor reaches the same Micro-Cluster page regardless of which door they walked through; what changes is content emphasis at that page, per §22's existing Dual-Behavioral Routing (Layer 1 narrative emphasis for Discovery-origin traffic, Layer 2 directory emphasis for Directory-origin traffic) — this section doesn't invent that adaptation, it confirms the URL structure it implies. This also satisfies a stated navigation requirement directly: Hub, Geo-Hub, and Cluster are each independently addressable, so a visitor — or a breadcrumb trail — can move between the three as separate stops.

An earlier draft additionally proposed a colon-delimited composite format (`hub_[identifier]:geo_[zone]:cluster-[id]`) as a second, bottom-up-specific slug pattern. That's retired as a URL — it doesn't support independently addressable levels or breadcrumb navigation the way a nested path does. If a composite key is still useful, it exists only internally, as a lookup/dedup mechanism analogous to `composite_hash` on `entities` (§9, ADR 0012) — never rendered in the address bar.

**Migration note, corrected against the real live code (2026-09-23):** there is no live `/get-local` route to migrate from and no 301 redirect needed — `/directory/index.php` and `/discovery/index.php` are already the real, live route names, confirmed directly from the site export. `/get-local`/`/explore` never existed as real routes; the earlier version of this note assumed otherwise from document-only reconciliation. `/directory/` is already a substantially-built page (category filter, search/sort/map). `/discovery/` is real but still a placeholder, with region cards live from the `hubs` table.

**Reserved-slug collision priority, confirmed real:** a real folder name always wins over a hub slug at the top level — `directory`, `discovery`, `listing`, `admin`, `api`, and similar reserved paths are checked before a request is ever treated as `/[hub-slug]`. A future hub cannot be named `directory` or similar without colliding.

**"Get Local" / "Let's Explore" are retained UI names, distinct from the technical route names.** The real, live account dashboard still refers to the two gateways by these names in user-facing copy (e.g. "used when you open Get Local directly and search," "a region you arrive through, for example from Let's Explore, always wins"), even though the underlying folders/routes are named `/directory/` and `/discovery/`. Both names should be treated as intentional and current — not a drift to reconcile away — unless a future decision explicitly renames the marketing copy to match the route names.

**Naming, resolved:** "Continental Hub" is the correct term for the top level — confirmed by the Ancient America blueprint, which states the platform plans 20 Continental Hubs total (§22 below covers the pattern; `regions.md` covers this pilot instance of it). Earlier engineering-blueprint language (§10) calling it "macro-hub" is the stale term and should be corrected there.

**Pilot staging:** the platform seeds outward from a single pilot region before scaling — a 200-mile operational radius centered on a regional hub, used to map collections of intent and deploy resources to an identifiable set before going wider. See `decisions/0006-pilot-hub-scope.md` for which region and why.

**Two more tiers beneath Micro-Cluster, neither addressable in the URL (`decisions/0042`).** The three route
segments above are unchanged, but a fourth and fifth tier now exist underneath the Micro-Cluster as resolved
data, not new path segments:

- **Anchor** — the cluster's primary municipal entity, picked automatically when a cluster's town pool has
  more than one candidate: county seat status first, then incorporated-municipality ranking, then a
  centroid/numeric fallback. The Single Home Rule binds every listing 1:1 to this resolved anchor. The
  anchor's name feeds the cluster slug directly: `slug = "cluster-" + tier_id + "-" + lowercase(anchor_name)`
  (e.g. `cluster-1a-st-johns`), so the listing URL is `/[hub-slug]/[geohub-slug]/[cluster-slug]/[listing-id-or-slug]`.
- **Sub-group** — unincorporated subdivisions, ranch communities, and colloquial place names sharing the
  anchor's ZIP (e.g. "Red Sky Ranch"). These are captured as alias metadata on the cluster, validated against
  land records or postal/historical registries, and are discoverable by that alias without ever getting their
  own slug or changing the cluster's primary one.

Micro-cluster auto-seeding also changes under the same decision: what's built today (`resolveMicroClusterId`)
stubs one micro-cluster per unmatched ZIP with no grouping logic — the ~40 "ZIP XXXXX (auto-seeded, needs
review)" rows this produced are being re-clustered under a real spatial algorithm (as amended 2026-09-28:
20-mile join radius, at most 5 towns, and at most 50,000 residents where Census population is known)
rather than left as permanent stubs. A separate `system_override` source (confidence 1.00) force-binds
low-density, high-value outliers (tourist corridors, historic registers) outside that algorithm entirely. See
`decisions/0042-five-tier-taxonomy-anchor-resolution-and-density-clustering.md` for the full design and its
open items — notably, how the nested `.../[cluster-slug]/[listing-id-or-slug]` listing URL reconciles with
the flat `/listing/{slug}` route this document and `decisions/0020` already depend on, which that ADR flags
but does not resolve.

## 20. Data Collection Guardrails & Exclusions

Ingestion (both automated crawling and user-generated content) is restricted strictly to public utilities, commerce, and regional heritage data. Systematically excluded by design and by the Tier 4 quarantine engine: private networks, password-gated databases, adult-only material, and private personal or sensitive government records. This is a hard boundary on what the platform will ever ingest or surface, independent of the HITL review process described in §7 and `decisions/0005-hitl-ai-guardrails.md` — HITL governs whether ingested content is trustworthy; this governs whether it should have been ingested at all.

## 21. Design Tension: Fluid Intelligence vs. Rigid Integrity

A recurring design question — how open should the system be before openness becomes noise, and how strict before strictness becomes a corporate directory again — resolved per-dimension:

| Dimension | Too Rigid | Too Loose | Balanced Approach (adopted) |
|---|---|---|---|
| Data Collection | Misses grassroots shifts, hyper-local anomalies, emergent trends. | Drowns in bot-driven spam and commercial noise. | Unrestricted macro-level capture via `CrawlerIngest.php`, filtered through strict quality gates. |
| Taxonomy | Forces unique regional ecosystems into standardized, corporate boxes. | Chaotic, overlapping categories that fracture local search integrity. | Bottom-up clustering anchored around natural geographic corridors and behavior telemetry. |
| Community Input | Stifles organic discourse; becomes a top-down directory. | Allows bad actors, anonymous bias, pay-to-play manipulation. | Self-governed topic hubs balanced by the Dual-Accounting model. |

This table is a design-principles reference, not a new rule — each "balanced approach" cell restates a decision already made elsewhere in this document (§7, §9, §18) and cross-referenced from here rather than re-argued.

## 22. Continental Hub Structure & the Single Home Rule

The platform scales through a three-level geographic hierarchy: **Continental Hub** (one of 20 planned, each a broad multi-state region) → **Geo-Hub Zone** (a macro span within a Continental Hub, roughly 3,000–25,000 sq. mi.) → **Micro-Cluster** (3–5 neighboring towns, a bounded local business pool). `regions.md` documents the full breakdown for the pilot Continental Hub; this section defines the pattern itself, once, so it isn't re-described per hub.

Within that hierarchy, each Continental Hub runs two content layers side by side (called "Tier 1 / Tier 2" in the source blueprint — renamed here as **Layer 1 / Layer 2** to avoid colliding with the unrelated Tier 1/2/3 *build-state* model in §1, which is a different axis entirely: build status vs. content type):

- **Layer 1 — Macro-Editorial, the Editorial View / Authority Engine:** broad geographic corridors carrying high-level historical authority content, deep-dives, and multi-day travel itineraries. Captures organic search traffic and routes visitors along natural historical trajectories. Serves the Traveler track.
- **Layer 2 — Micro-Cluster Directory, the Directory & Utility View / Conversion Engine:** tight municipal/economic radii with a bounded business pool per cluster, stripped of tourism content, serving residents a clean local directory. Serves the Resident track.

**Naming note, 2026-09-24: this is the same Layer 1/Layer 2 split as `commercial.md` §0's Directory/Discovery duality, now consistently named — not a second, competing architecture.** `commercial.md` §0 already retired "Dual-Engine Architecture" as an independently named concept, resolving that the Authority Engine (Editorial View) and the Conversion Engine (Directory & Utility View) are two angles on this one duality, not two parallel systems — Layer 1 above *is* the Authority Engine's operating layer, Layer 2 *is* the Conversion Engine's.

**Which geographic level each view actually operates at, pinned down precisely against what's already built — correcting a real granularity mismatch rather than restating it as given:** the Editorial View's actual operating unit is the **Geo-Hub Zone**, not the Continental Hub. `regions.md`'s Geo-Hub Zone names ("The Ancient Borderlands & Painted Desert," "Historic Old West & Border Frontier," etc.) are themselves the narrative corridors — `commercial.md` §7's Foundational Macro & Geo-Hub Guides are written "per Strategic Sub-Hub" (the business-side name for a Geo-Hub Zone, see §3 below), and the Pre-Colonial Heavy / Frontier & Industrial Transition thematic overlay (`regions.md`) is classified at Geo-Hub Zone granularity specifically *because* a single Continental Hub (Ancient America) visibly contains zones on both sides of that split — a Continental Hub can't be treated as one narrative corridor without erasing exactly the differentiation that overlay exists to preserve. The Continental Hub is the outer named umbrella a set of Geo-Hub Zones sits inside (its own broad regional identity, e.g. "Ancient America"), not itself the unit the Authority Engine writes at. The Directory & Utility View's partner-facing operating grid is also the Geo-Hub Zone (`commercial.md` §3's "~12 Strategic Sub-Hubs per Continental Hub" is this same figure, the unit the 24,000-partner nationwide target scales against) — but the actual end-user-facing search/listing granularity nests one level deeper, at the **Micro-Cluster**, matching Layer 2's definition above. So: Continental Hub (umbrella identity) → Geo-Hub Zone (the unit both views actually operate at — narrative corridor for the Authority Engine, partner-scaling grid for the Conversion Engine) → Micro-Cluster (the Conversion Engine's actual consumer-facing search/directory unit).

**Dual-Behavioral Routing:** local users are routed straight into Layer 2 (locked to their immediate radius); global visitors are led with Layer 1 content, with contextual hand-offs into the local directory as they move through a route.

**The Single Home Rule:** every business profile is assigned exactly one permanent Primary Home Zone, based on its physical address, enforced structurally rather than left to convention. This is what prevents a single business from being duplicated across multiple micro-clusters (database bloat) while keeping local search results precise. This is the rule `charter.md` refers to but doesn't itself define — the principle belongs in the Charter, the enforcement mechanism belongs here.

**Discovery Guides at every level (`decisions/0043`).** Each level of this hierarchy, down through the
Anchor and Sub-Group tiers `decisions/0042` added, gets its own Discovery Guide, the place's "knowledge":
a Story (crawler-drafted, human-approved per `decisions/0005`), a Place Profile (population and
demographics rolled up over its ZIPs), a Local block (listing counts plus a link into the Directory filtered
to that place), Chameleon picks woven into the story, and links to the next level down.

## 23. Shared Place Context (Real, Substantially Built — Supersedes the Earlier "Personalized Insight Engine" Placeholder)

**This section previously described a speculative "Personalized Insight & Productivity Engine" with no schema and no real design.** The real platform spec and live code (2026-09-23 export) show the actual, much more concrete system that already exists under this heading: **Shared Place Context** — one model answering "where is this visit?" for the location icon, search scope, business breadcrumbs, and admin hub-scoping, shared by both gateways (§4) rather than owned by either.

**Shape:** `{ level: hub | geo_hub | cluster | city | zip, id, label, lat, lon, radius, source }`, resolved server-side (`/api/place.php`) and exposed to the browser as one object.

**Source precedence, first match wins:**
1. **Picked** by the visitor this visit (a ZIP, city, or hub).
2. **Arrived from** a region via the Discovery gateway or a hub/geo-hub/cluster URL — this always wins over a saved default.
3. **Saved default**, for a signed-in user, applied only on a direct Directory visit when they search. Users can save up to several places (managed from their account dashboard, one marked default) and switch between them from a place picker. Never applied on Discovery or funneled pages.
4. **Device guess** — never applied automatically; offered as a suggestion ("Looks like Phoenix. Use this?"), with an "approximate" note when accuracy is poor.
5. **None** — shows a region picker, never the whole unscoped directory.

**Real schema, live:** `users.area_zip`/`area_city`/`area_state`/`area_lat`/`area_lon` (migration 007) is the primary resolution source — comprehensive, matches what real search and hub navigation already use. `users.home_cluster_id` is retained as a secondary, best-effort derived field for cluster-scoped features generally. A separate `user_places` table (`user_id`, `label`, `level`, `scope_slug`, `zip`, `city`, `state`, `lat`, `lon`, `is_default`, `sort_order`) holds a signed-in user's saved places, deliberately with no foreign key back to `users` by design. The account dashboard's real "Saved Places" UI (add/remove/make-default, up to 10) is live against this table today.

**Rules enforced server-side, not just in the UI:** the resolved place is always visible ("Showing: Four Corners & Colorado Plateau · change"); a named lookup (a business name, a typed city) ignores scope entirely; scope is enforced in the search API itself, not only client-side; no place and no query/category shows the region picker rather than the full unscoped directory.

This is a real, live, mostly-built system — not a future capability needing a first design pass. What remains open: registration-time capture of an "area of interest" (blocked on a real constraint — registration doesn't create a session, so this needs new server-side handling inside the registration flow itself, not a reuse of the authenticated save-place endpoint), and international/other-region visitor support, which is explicitly a data-coverage gap (no `zip_coordinates`/hub rows exist outside the US, let alone outside the pilot trade area) rather than a UI or architecture gap.

Whether a given user's activity may feed any future recommendation/insight layer built on top of this substrate remains governed by `decisions/0010-identity-exposure-and-ai-consent.md`, unchanged from the earlier version of this section.

## 24. Privacy & Regulatory Disclosure Position (GDPR/CCPA)

*This section records Traversence's working position on data-privacy disclosure so product and engineering decisions don't silently drift out of step with it. It is not legal advice — the applicability of GDPR (which turns on whether the platform processes data of people in the EU/UK) and CCPA and similar state laws (which turn on California/other-state residency, revenue, and data-volume thresholds) to this specific business should be confirmed with qualified counsel before launch, not assumed from this document.*

**What this platform collects that a disclosure needs to cover:**

- **Guest correlation data** — `guest_session_id` cookie and, as a fallback, IP-based clustering (§7, §11; `decisions/0009-guest-activity-attribution-and-pattern-detection.md`). Pseudonymous, not tied to a name, purpose-limited to source attribution, conflict resolution, and abuse-pattern detection, retained on a rolling 30-day window.
- **Authenticated user activity & telemetry** — every write carries `actor_user_id` and, where applicable, `acting_as_listing_id` (ADR 0002, ADR 0008; mechanism documented in §5), feeding trust scoring, the DIKW pipeline, and — once built — the Personalized Insight & Productivity Engine (`prd.md`, Tier 3 — this section no longer describes it; see §23 above for why).
- **Business/listing data** — ownership, verification, and contact records tied to `ListingId` (§9, ADR 0002).
- **Chat logs** — raw streams retained 90 days on a rolling window before purge (§14).
- **Home location** — Country (every registrant) and, for U.S. registrants, Zip (City/State auto-resolved from `zip_coordinates`, never free-typed) — captured at registration for regional search auto-scope (`users.home_cluster_id`). Added 2026-09-24, `decisions/0027-international-registration-gate.md`.

**Disclosure obligations this creates, at minimum:**

- A privacy policy naming each purpose above explicitly, in plain language — not a generic "we collect analytics" statement. Purpose limitation (data used only for what was disclosed) is the operative principle throughout this document already; the policy should say so.
- A stated retention period for each data category (this document already fixes several: 30 days for guest correlation data, 90 days for chat logs, a 30-day grace period before permanent account-deletion purge per §14) — a privacy policy should mirror these rather than stating a separate, undocumented schedule.
- A mechanism for a registered user to request access to, or deletion of, their own data. §14's account-deletion flow (30-day grace, then anonymization via `DELETED_USER_UUID`) is a start; formal data-access/export requests (a GDPR/CCPA "right to know" or "right to access" request) aren't yet designed anywhere in this document.
- A "Do Not Sell/Share My Personal Information" posture under CCPA. The Content-to-Commerce Engine's zero-commission, no-ad-network model (`commercial.md` §9) is a genuine head start here — if the platform never sells or shares personal information with third parties for advertising, that should be stated as an explicit, affirmative disclosure rather than left implicit.

**Resolved, 2026-09-24 — jurisdictional scope and cookie posture.** `decisions/0025-gdpr-ccpa-jurisdictional-scope-and-cookie-posture.md` resolves what were the first three open items here: GDPR is out of scope on the intent/targeting test (Article 3(2)) — no EU/UK marketing, no Euro/GBP pricing, a North America-only roadmap — to be stated as an affirmative disclosure, not left silent. CCPA is out of scope today on a threshold basis (volume/revenue nowhere close, and the "sells personal information" prong structurally, permanently inapplicable given the zero-ad-network model), to be revisited if a California-based hub's volume ever approaches the thresholds — unlike the GDPR position, this one isn't permanent. A direct code audit (`login.php`, `register.php`, `session.php`, `Auth.php`, and related files) found only strictly-necessary cookies exist (the native session cookie and `guest_session_id`) — likely no cookie-consent-banner obligation currently exists at all. `decisions/0027-international-registration-gate.md` is the registration-time mechanism that operationalizes the GDPR position with an actual technical safeguard, not just a documented intent.

**Resolved, 2026-09-24 — DSAR handling.** The fourth open item here — a generic data-access/export/deletion request flow — is resolved by `decisions/0026-dsar-export-and-erasure-pipeline.md`: an export mechanism (new), an erasure trigger that executes synchronously on verification rather than waiting on the existing §14 grace period, and a legal-hold exception reusing `is_suspended` with `decisions/0019`'s DMCA retention as its grounding for anything DMCA-linked.

These resolutions remain documentation-level determinations, not legal advice — confirming them with qualified counsel before launch is still the right posture, per the disclaimer at the top of this section.

**Resolved, 2026-09-24 — no longer an open item.** Whether and how users consent to their contributions being used as input to AI-generation systems (§23, §26) is settled by `decisions/0010-identity-exposure-and-ai-consent.md`, fully Accepted with no open parameters: AI grounding material is de-identified by default (no consent gate needed), and the narrower case where identity would actually attach to AI output (e.g. the Personalized Insight & Productivity Engine, §23) requires an explicit control that **defaults to opt-in (off)** — a user's identified activity never reaches that kind of pipeline until they actively turn it on. The disclosure obligations list above should name this control directly once the privacy policy is drafted, per the pre-work item now logged in `prd.md`'s Tier 3 entry for §23.

## 25. AI Content Generation Pipeline: Scraper-to-Article Journey

The concrete, end-to-end mechanism behind the Content-to-Commerce Engine's Contextual Discovery stage (`commercial.md` §0) — how a partner's own product/listing data becomes a published editorial article that routes traffic back to them. This pipeline is a paid-tier feature entirely: Free listings have no access to it at all (`commercial.md` §1's Free Tier Specification) — everything below applies from Core upward.

**Four parties in this journey:** the **Administrator** (manages scraping, enrichment, review, and publishing — the technical role defined in §11, not the community Steward), the **listing** (the underlying product/business data being written about), the **article** (the front-end discovery content produced), and the **reader** (the discovery-side visitor the article is ultimately written for). Keeping these distinct matters because the pipeline below has a human decision point (an Administrator) between every automated step and the next.

1. **Dual-Mode Scraping & Ingestion.** `CrawlerIngest.php` (the same scraper subsystem behind the `ingestion-scrape-queue`, §10 step 6, §12) runs in one of two modes: **Targeted**, pointed at a specific, predefined source (a partner's own catalog page, or a named manufacturer's product line) to pull precise data; or **Free-Range**, a broader discovery crawl within strict safety guards and predefined pre-scraping policies to map a wider industry or product ecosystem before any article work starts. Either way, raw output lands in a centralized, structured data repository — a stored corpus — rather than being processed on the fly; nothing downstream works directly off a live scrape. Ingested data becomes `entities` and `entity_metadata` records (§9) in the graph-mirror, the same as any other ingested source. **Claim-aware matching (corrected to the real, field-level mechanism — see §9, ADR 0012):** every incoming record is checked against `composite_hash` to recognize a listing that already exists rather than create a duplicate — including one already claimed and verified. There is no separate `listing_ownership` table in the real system and no record-level "route the whole match to HITL" rule: protection is enforced per field, via `is_locked` on `entities`/`entity_metadata`. A field a human (owner, admin, or high-trust user) has directly edited is permanently immune to a later scrape regardless of recency; any field nobody has touched can still legitimately absorb new crawler data even on an already-verified listing. This is ADR 0005's "no automated output overwrites organic human context" guarantee, made concrete at the field level for re-scraped, already-claimed listings.
2. **Draft Generation & Enrichment.** The AI content engine (the mechanism behind the tiered "AI-engine content assistance" language in `commercial.md` §1) ingests the stored corpus — not a live feed — to transform it into draft articles, one variant per distinct product/listing configuration rather than a single generic write-up (e.g., 14 separate articles from one catalog of 14 shed models). The bar for a finished draft (the "Enrichment Bar") is explicitly higher than specs and pricing: the article must explain *why* a reader would choose that specific variant (storage capacity, tiny-home livability, material durability), and it must embed at least one concrete **Connection Point** — a real-world experience or utility tied to the content, not just abstract description — making the article immediately actionable for the reader. ("Connection Point" here is the same concept `charter.md`'s "Living Connection Points" paradigm names at the platform level, applied at the level of a single article.) Reaching that bar is iterative: see §26 for how topic selection and re-scraping refine the source material before a draft is considered ready.
3. **HITL Gate — this pipeline's output is System-Created Content, unaffected by `decisions/0005`'s 2026-09-24 amendment.** No draft publishes automatically. Every AI-generated catalog article passes through the same Tier 4 quarantine/admin-review pipeline as any other ingested or AI-assisted content (`decisions/0005-hitl-ai-guardrails.md`), exactly like autonomous seeding (§7) and guest contributions (`decisions/0009-guest-activity-attribution-and-pattern-detection.md`). This is an Administrator sign-off, not a Steward one (§11). This pipeline's articles are the Authority Engine's own editorial voice (`commercial.md` §7), not a partner writing their own words — `decisions/0005`'s System-Created bucket, not its Self-Generated Partner Content exception. Draw the line by content type, not tool use: a partner's own AI-assisted seasonal update or profile description is a different thing entirely, and is governed by that amendment instead.
4. **Discovery & Traffic Routing.** Once approved, the article publishes into `/discovery/` (Top-Down / "Let's Explore," §4) with the originating listing's `ListingId` attached as a graph-mirror connection back to that entity (§9). A reader who lands on the article is routed — via the Chameleon Filter (`decisions/0003-chameleon-filter-routing.md`) and the dual search engines — back to the listing profile and ultimately the partner's own listing URL, while the same engines surface other contextually related resources alongside it. **Neutrality is preserved throughout:** this routing stays zero-ad and non-pay-for-rank (ADR 0007) — baseline organic discovery is identical regardless of tier. What scales with tier is *integration depth*, not rank: higher tiers get deeper discovery integrations, smarter contextual cross-linking, and broader resource surfacing, which drives more relevant, higher-intent traffic without ever using tier or payment as a ranking input. This is the Contextual Discovery stage of `commercial.md` §0 made concrete at the mechanism level.
5. **Tiered Quotas — first-draft numbers set 2026-09-24 (`commercial.md` §1).** How many draft articles a partner's catalog can generate scales with subscription tier starting at Core — Free has none of this (step-zero exclusion, `commercial.md` §1). Core: up to 5 catalog articles/month. Strategic: up to 25/month, plus up to 4 custom partner content pieces/month (seasonal updates, event posts). Cornerstone: no monthly cap — every distinct catalog variant gets an article, bounded only by the partner's actual catalog size, regenerated when the underlying item changes. These are explicitly flagged in `commercial.md` §1 as first defaults, not tuned numbers, same status as `decisions/0024`'s classifier thresholds — real usage data will size them properly once it exists. **A second, separate axis — who operates the tools, not how much they can produce — is layered on top, per direction 2026-09-24:** Core is self-service only (the owner/manager generates and publishes their own content, no admin/White-Glove involvement); Strategic and Cornerstone add admin/White-Glove-supported content creation and publication on top of the same tools. This support-level axis changes nothing about step 3's HITL gate — every tier's catalog articles pass through the identical Administrator sign-off before publishing to `/discovery/`, self-service or admin-supported alike. See `commercial.md` §1 for the full framing.

## 26. AI Topic Extraction & the Framing–Scraper Feedback Loop

How the AI engine decides *what* to write about, distinct from §25's *how* it produces a draft:

- **Extraction & Selection.** The AI engine processes the stored corpus (§25 step 1) to analyze, summarize, organize, and synthesize it into selectable topics. An Administrator or the content-owning partner selects which extracted topics to actually pursue and can define a context scope for that selection — topic selection is a human decision, not an autonomous one, consistent with the HITL principle applied everywhere else in this document.
- **Top-Down / Bottom-Up Integration.** Every article blends both context layers rather than picking one: top-down structural context (which Continental Hub / Geo-Hub Zone / Micro-Cluster it belongs to, §22) and bottom-up local detail (specific geography, community data, the listing's own attributes). This is the Layer 1 (Macro-Editorial) / Layer 2 (Micro-Cluster Directory) split already defined in §22, applied at the level of a single article rather than a whole hub.
- **Framing → Scraper Feedback Loop.** Once a topic and context scope are selected, they activate a specific writing framework — a template/structure appropriate to that topic type — and that framework commands the scraper to retarget specific sources for deeper, more specialized context. The framework doesn't just trigger a generic re-scrape; it configures *which* source the scraper targets. Example: if the extracted topic is "sheds" and the listing's manufacturer is a named supplier (e.g., a manufacturer such as "ABCO"), the framework points the scraper at that manufacturer's own page or documentation rather than a generic search. Each pass sharpens the source data and a relevance score before drafting begins, so the AI writes from a deeply informed baseline rather than generic assumptions. Ingestion becomes demand-driven at the topic level, rather than a single bulk import the AI works from afterward.

**Community thread content feeds relevance, never article substance.** Content from Communities & Groups (§27) may be staged into the same corpus used for topic extraction above, contributing to context-relevancy and topic-relevance scoring — but it is never used as direct or verbatim source material for a published article. The framing→scraper feedback loop above always re-gathers independent, publicly-sourced grounding material to actually write from. This separation, and the deeper data-minimization rule governing what from that corpus is even stored in the first place (raw content in, only classified abstractions out), is defined in `decisions/0011-context-in-abstraction-out-data-minimization.md` and summarized in §28.

**Open question, not yet resolved:** how deep this feedback loop is allowed to run before it needs its own HITL checkpoint. A single re-scrape for grounding detail is a very different risk profile from an unbounded chain of scraper calls triggered by AI-selected framings — worth a decision before this loop is built, not after. Consent for using a *user's own contributions* (as opposed to a partner's own catalog data, or a manufacturer's own published material) as grounding material for this loop is governed separately by `decisions/0010-identity-exposure-and-ai-consent.md` (de-identified by default; identity-attached use requires opt-in/opt-out per that decision). A related infrastructure note: `topic_id` embedding storage and similarity search should sit behind a clean internal service-layer abstraction from the start (see `decisions/0004`, revised), since MySQL/MariaDB lacks solid native vector-index support today — that keeps a later move to Postgres/`pgvector` (or a dedicated vector store) from requiring a rewrite of every caller.

## 27. Communities & Groups Architecture

**Naming note (2026-09-23):** the platform's own live spec has a per-Micro-Cluster discussion feature logged under a working name this document deliberately does not use or reference anywhere, per explicit instruction. If a geography-bound discussion feature like that is ever built, it should be scoped and named fresh against the model below rather than adopting that other name or schema wholesale — this document's Communities & Groups model (topic/interest-bound, not geography-bound) stands on its own and isn't reconciled against it.

Distinct from the platform-wide governance charter (`charter.md`) and from the Continental Hub / Geo-Hub Zone / Micro-Cluster geographic hierarchy (§22) — communities are user-created, topic- or interest-bound spaces that sit alongside geography rather than being drawn by it.

- **User-derived creation, not admin/steward-drawn.** Communities are created by users, not assigned top-down by an Administrator or Steward. The system's role is to gate who is allowed to create one and to provide the structural tools (charter template, privacy controls), not to originate community boundaries itself.
- **Steward assignment, not election (2026-09-23, per direction — see §11/§14).** Creating a community automatically seats the creator as its first Steward — a direct consequence of creation, not a separate step. A community supports more than one Steward at once: any existing Steward can appoint another member as a co-Steward directly, a plain assignment with no vote or waiting period. This means a healthy, actively-led community should rarely if ever need `PENDING_STEWARD_ELECTION` (§14) — that mechanism now exists purely as the last-resort path for a community that's lost every one of its Stewards with no successor appointed. This needs its own schema (a `community_stewards`-shape join, not a `users` column — stewardship is per-community and multi-holder, so it can't live as a single global value on the user row) when §27 gets its technical-design pass.
- **Per-community charter, distinct from the platform Charter.** Every community is bound to its own user-authored charter — a short document the creator writes when standing up the community, separate from and subordinate to `charter.md`. This per-community charter serves two roles at once: it's the conduct rules for that specific space, and it's the access-control configuration (public vs. private, any screening questions required to join). Search and discovery of the community (see visibility model below) surface charter-derived metadata, not thread content.
- **Creation gating.** Standing up a new community is gated by a combination of: account standing/trust metrics (reusing `TrustScore.php`, §7 — the same signal already used for platform-wide trust weighting, not a parallel scoring system), penalty and restriction history (a user with recent moderation actions against them faces a higher bar or an outright block on creating new spaces), and structural creation friction built into the creation flow itself (naming, choosing a privacy level, and writing an initial charter are all required steps, not skippable defaults — friction by design, not accident).
- **Post-creation visibility is signal-based, not a blanket timer.** A flat "every new community is suppressed for N days" rule (the common large-platform pattern) was considered and rejected: in a brand-new pilot Continental Hub or Geo-Hub Zone, *everything* is new by definition, so a blanket new-content suppression rule would throttle the very growth the pilot depends on (§19's pilot-staging model). Instead, visibility suppression is triggered by actual risk signals — low trust score, a pattern of serial community creation by the same account, recent penalty history — the same inputs used for creation gating above, applied continuously rather than as a one-time gate.
- **Three-tier visibility model:**
  - **Guest** — read-only, macro-scope only. A guest can see that communities exist as a category of the platform (consistent with §7/§11's general read-only guest boundary) but gets no access to any individual community's threads, and communities are excluded from guest-facing search results entirely.
  - **Registered, non-member** — can discover a specific community's existence and its charter-derived metadata (name, description, privacy level, stated purpose) through search, exactly like any other searchable entity in the graph-mirror (§9). Cannot see inside its threads.
  - **Member (joined)** — full access to that community's threads, per whatever that community's own charter specifies. Joining is the gate to seeing inside — not registration alone.

  **Existence is searchable; thread content is not.** A community's existence and its charter-derived metadata are indexed and searchable like any other entity. Thread *content* is never searchable and is strictly join-gated — this holds regardless of a community's public/private charter setting, which governs who may join, not whether joined-member content becomes searchable.

- **User-to-user escalation ladder (Level 1/2/3).** Named "Level," not "Tier," specifically to avoid colliding with the unrelated build-state Tier 1/2/3 model (§1) and the Tier 4/HITL quarantine pipeline (`decisions/0005-hitl-ai-guardrails.md`) — the same naming-collision principle already applied to Layer 1/Layer 2 in §22.
  - **Level 1 — Peer-to-Peer, self-serve.** Block, mute, report — the user-side safety controls already established in `decisions/0010-identity-exposure-and-ai-consent.md` and `prd.md` Tier 2. No community or platform staff involvement required.
  - **Level 2 — Behavioral Conflict → Group Charter Steward.** Disputes and charter violations inside a specific community escalate to that community's Stewards (§11 — a community can have more than one) for resolution, per that community's own charter.
  - **Level 3 — System/Data Abuse → System-Level Admin.** Anything beyond community-level conduct — platform abuse, data misuse, cross-community harassment — escalates to Administrator (§11), the same technical/system-access role that handles HITL review elsewhere in this document.
- **Guest-abuse interaction with communities.** A report against guest misbehavior inside or around a community feeds the guest-risk-scoring mechanism already defined in `decisions/0009-guest-activity-attribution-and-pattern-detection.md`. That ADR now carries an explicit default for the soft-action/hard-action split this raises — see its Consequences section.
- **Communities and the AI corpus.** Community thread content can be staged into the same corpus that feeds topic extraction (§26) — contributing to context-relevancy and topic-relevance scoring — but is never used as direct or verbatim source material for a published article, and raw thread content is never persisted into that corpus in identifiable form to begin with. See §28 and `decisions/0011-context-in-abstraction-out-data-minimization.md` for the full data-minimization mechanism this depends on.

**Not yet ready for engineering handoff.** This section defines the governance model (who may create, how visibility works, how disputes escalate) but no schema (communities, memberships, per-community charters, the escalation-ladder state machine) or API contract exists yet. A developer cannot start building this model from this section alone — it needs a follow-up technical-design pass before implementation begins.

## 28. AI-Corpus Data Minimization: Context-In, Abstraction-Out

Governs what actually gets written to the stored corpus (§25 step 1) that AI systems read from — distinct from §26, which governs what topics get *selected* from it once it's there. See `decisions/0011-context-in-abstraction-out-data-minimization.md` for the full decision and rationale; this section records the resulting mechanism.

- **Classify at intake, store only the classification.** Incoming content — from any source: community threads (§27), guest submissions (§7, §11), scraped external content (§25), or reviews — is read in full to make a good classification judgment, but only the resulting abstracted category is written to the corpus: relevancy, topic, context, summary, listing-specific, experience, recommendation, and audience/impact. Raw verbatim content is never persisted into the shared corpus.
- **Summary must generalize, not paraphrase.** A summary field that stays too close to the source text reopens the same fingerprinting risk raw storage would have created; genuine generalization is a hard requirement on that field, not a style preference.
- **Who/What/Where/When/Why + noun/verb keying.** Structured keys (e.g., a named local landmark or road) let the system recognize that something is a topic worth tracking without storing the private conversational content it came from. **"Who" means audience/impact/usefulness** — which persona or audience segment a topic serves (the Resident/Traveler/Community tracks, or a finer segmentation beneath them) — **never** system-user identity, which stays exclusively governed by `actor_user_id` / profile attribution per `decisions/0010-identity-exposure-and-ai-consent.md`. Audience/impact classification is derived dynamically from the full surrounding conversational context at classification time (context-in), while only the resulting category is stored (abstraction-out) — the same principle applied one layer further in.
- **Frequency-gated topic promotion.** A key is only promoted to legitimate "topic scope" after it recurs across multiple independent mentions. This structurally — not just by summary quality — prevents a one-off private detail from a single gated conversation from ever surfacing as a public trend, since a single mention can't recur.
- **Sensitive-source tagging survives into retention/access rules.** Any staged data sourced from a sensitive context (e.g., a gated community thread) is tagged by source at staging time, so retention and access rules can target that flagged slice specifically rather than relying on uniform treatment of a mixed corpus.

## 29. DMCA Notice-and-Takedown (Proposed — Real Legal Prerequisites Outside This Document Set)

**Added 2026-09-24, per direction. See `decisions/0019-dmca-notice-and-takedown.md` for the full decision; this section records the resulting mechanism.** Deliberately a separate flow from §9's dispute mechanism — a dispute asks "is this the real owner," a DMCA notice asks "does this specific content infringe a copyright," and the two have different targets (`entities.status`/ownership vs. a specific `entity_metadata` field), different statutory obligations, and different admin access scoping.

- **Intake is form-validated, not human-reviewed for completeness.** `/dmca-notice.php` structurally requires all six statutory elements (identification of the work, the specific `entity_id`/`entity_metadata` target, filer contact info, a good-faith-belief statement, a perjury-and-authorization statement with a typed legal name as a legally valid electronic signature, and — optionally — supporting documentation via `decisions/0017`'s existing upload path, extended with a new `dmca_notice` value on `related_type`). A new `dmca_notices` table tracks each notice through `received → removed → counter_noticed → restored` (or `litigation_hold`, or `invalid` for a facially incomplete notice).
- **Removal is fast execution, not a merits review — the one place in this platform's governance where less deliberation is the legally correct posture, not a shortcut.** The perjury statement shifts liability for a false claim onto the filer; the platform's obligation is to act expeditiously on a facially complete notice, not adjudicate whether the underlying claim is true. `admin/dmca.php` is **super_admin only** — a deliberate departure from every other admin action in this document set being hub-scoped, since copyright law has no geography and this concentrates a real legal-exposure surface with the smallest, most consistent admin group. Removal targets the specific `entity_metadata` row when identified, or reverts the whole entity to the same baseline crawler-display `decisions/0015` already built for disputes when it isn't — reused, not reinvented.
- **Repeat-infringer tracking is a legal precondition for safe harbor, not optional.** A `dmca_strike_count` on `users` reaching 3 (a first default, matching common practice) trips the already-real `users.is_suspended` flag — no new enforcement mechanism. This policy has to be publicly posted (Terms of Service) to actually satisfy the statute's "reasonably implemented" requirement — a real prerequisite, not a nice-to-have.
- **Counter-notice and restoration follow the statute's own 10–14 business day window, not a platform-chosen number.** A counter-notice starts `restore_eligible_at = NOW() + 10 business days`; restoration is **automatic** once that window closes unless a super_admin has logged a `litigation_hold` after actually receiving notice of a filed lawsuit — there's no way to automate detecting that. This is the second deliberate, narrow exception to this platform's "no automated consequence without a human sign-off" default (the first being §9's `claim_abandoned`), and it's legally required rather than a convenience.
- **Two real prerequisites this document set cannot resolve on its own, flagged plainly rather than implied as done:** a designated DMCA agent must actually be registered with the U.S. Copyright Office's online directory before any of this confers real safe-harbor protection, and the notice/counter-notice statutory language plus the repeat-infringer policy's public posting need real legal review before launch — the same posture §24's GDPR/CCPA section already takes toward needing counsel review. **The registration procedure itself, added 2026-09-24 per direction:** create an administrative account at `dmca.copyright.gov` (Login.gov-compatible), designate a Primary Contact and a required Secondary Contact (the backup that actually receives the three-year renewal alerts), verify the account by email, then "Add Service Provider" with the legal name, corporate address, all alternate names/domains/DBAs, and the agent's public contact info, and pay a **$6** fee by card or e-check. That $6 covers the service provider and every alternate name/domain/DBA under one filing — but a business operating through more than one separately incorporated legal entity needs a **separate $6 registration per entity**. The registration's contact info must be **publicly displayed on the site**, and it must be **renewed every 3 years** or safe harbor is lost entirely, exposing the platform to direct and secondary copyright liability for user content from day one. See `decisions/0019`'s Consequences for the full procedure.
- **Retention, resolved per direction: permanent, not `decisions/0017`'s 72-hour default.** A DMCA record (a `dmca_notices` row and any attached `verification_documents` with `related_type = 'dmca_notice'`) carries real statute-of-limitations exposure — civil copyright claims run 3 years under 17 U.S.C. § 507(b), extendable via the discovery rule or ongoing-damages claims — and since it's not knowable in advance which record a future legal challenge will actually need, these records are kept indefinitely rather than on any purge clock. `decisions/0017`'s cron now carries an explicit exclusion for this `related_type` rather than relying on these rows simply never reaching a purge-eligible state.
- **Content ID-style automated fingerprinting is explicitly out of scope.** That's a scale solution for platforms processing far more uploads than this one ever will; this platform's existing HITL-gated ingestion staging (`decisions/0005`) already provides a real, human-reviewed check before scraped content ever goes live, which most platforms this size don't have at all.
- **Registration & renewal management, added 2026-09-24 per direction — the platform now tracks its own DMCA registration rather than relying solely on someone remembering an external three-year date.** A new `dmca_agent_registration` table holds the publicly-displayed Designated Agent contact info (name, address, email, phone), the Copyright Office portal's own Primary/Secondary account contacts, and `registered_at`/`last_renewed_at`/`renewal_due_at`/`status`. A new **super_admin-only** page, `admin/dmca-settings.php`, lets a super_admin view and edit this record — distinct from `admin/dmca.php`'s notice-review queue, matching this section's existing "different action, different page" pattern. `/dmca-notice.php`'s public agent-contact display now reads live from this table instead of hardcoded page copy, so an update in one place stays accurate everywhere the law requires it to be shown. The existing daily cron (already used for `decisions/0017`'s purge and this section's own counter-notice restoration) gains a renewal check: within 90 days of `renewal_due_at` (a first default), status flips to `renewal_due_soon` and emails every super_admin via `Mailer.php`, escalating to `lapsed` — treated as a genuine incident, since a lapsed registration means no safe harbor at all — if the date passes with no renewal recorded. `admin/adminportal.php`'s DMCA tile surfaces this status as a visible badge. This tracks and reminds; it doesn't file the renewal itself — the actual $6 renewal still happens on the Copyright Office's own site, per the Consequences item below.
