## Audit item: IR-0001's root cause (runs #1288 and #1290)

**Evidence read:**
- Railway's logs for deployment `560ff94b` (crawler 2.16.0), 08:15–08:45 UTC, read-only.
- The crawler's code as it was live then (`open_load`, `site_call`, `_overture_release`, traversence `main` before
  2.16.1's change, which touched only Common Crawl).

**What the logs show:**
- `foursquare_bulk` (its run began at the 08:15 container start) logged `08:20:34 foursquare_bulk stopped:
  TimeoutError('The read operation timed out')`.
- `overture_bulk` (run 4fbc278e, started 08:25:30, its share 600 s) logged `08:31:41 overture_bulk stopped:
  TimeoutError('The read operation timed out')`.
- Neither run logged a town's "records sent", so both failed before the first town finished.
- Nothing else failed in those runs (refresh, identity and heritage did their work).

**What the code shows:**
- That error, as a plain `TimeoutError` with that text, is raised while waiting to *read a reply* on a urllib request.
  The Overture and Foursquare reads themselves go through DuckDB's httpfs, whose failures are DuckDB's own errors with a
  different message. So the timeout was not in reading Overture's or Foursquare's data.
- **The calls that can raise it:**
  - in both tasks: the site calls to `/api/crawl/loads.php` (the opening GET, 60 s; each 500-row POST, 120 s; the
    town's "done" POST, 60 s);
  - in Overture's only: the S3 release listing (30 s, to Amazon), which runs only when `OVERTURE_RELEASE` isn't set on
    Railway.
- Foursquare failed the same way, and it makes no S3 listing call. **The calls the two failures share are only those to
  our site's `loads.php`.**

**Finding:**
- **Confirmed:** the worker sent its request to our site's load endpoint, and no reply came within its timeout. It was
  not a data source (Overture or Foursquare), and not Railway.
- **Still open, as Jason put it: inside our load handler, or on the outbound/response path?**
  - "Read operation timed out" means the request was sent and the reply never arrived in time. That fits both the
    handler running too long and the reply being lost on its way back.
  - Settling it needs **our endpoint's own timings for those minutes:** the board's ledger rows for
    `/api/crawl/loads.php` (each call's duration and answer), 08:15–08:21 and 08:26–08:32 UTC, or Bluehost's access log
    for those requests (status, time taken). A ledger row showing the call finished (stored rows, a 2xx) after the
    worker's 120 s points to the response path. No row, or one still running, points to the handler.
  - **This needs live data**, so it goes in the session manager's one ask to Jason with step 3.
- **Which call it was**, the opening GET or a 500-row POST, can't be told from the logs: the worker logs no per-call
  timing.
  - Spec for the build: the worker logs each site call's duration and size (also in case #51's held draft).
  - Settling it also depends on whether `OVERTURE_RELEASE` is set on Railway, which decides if Overture's S3 listing
    ran. A variable *name* check is safe; I didn't read values.
