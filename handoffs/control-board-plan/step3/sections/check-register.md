## The four gaps (proposed checks)

Jason asked whether the audit checks "end to end … search on a page and its end points function correctly, the page load speed, the function speed, the photo loads and display … the brand of design standards". Four of those have no check today:

1. **TOOLS:** each tool and endpoint by every type of account. `site-audit/tools.md` doesn't exist, and 0145 §1's function and tool checks aren't built.
2. **LOAD:** a load time for every page against a target. The paths check flags only a page over 4 s on its way (`paths.mjs`, `SLOW_MS = 4000`), and the rendered check records only failures.
3. **PHOTOS-SHOWN:** every photo on a page shown. `photos-check.sh` proves the uploads rule, not that a page's photos are drawn.
4. **BRAND:** most of `brand.md`. Only R10 (icons), R11 (breadcrumbs) and the rendered check's 3px edges are automatic.

## One results format

One results format for every check, extending site-audit/results/findings.json (version, generated_at, findings[]). Each result is one row.

| Field | What |
|---|---|
| `check` | the check ID in the register (R01, RENDER, PATHS, LOAD…) |
| `item` | what it checked: a route, a path id, an endpoint, a workflow or a service |
| `who` | the account it ran as, where it matters |
| `target` | the target, as the register states it at the time |
| `result` | pass | fail | partial | no check |
| `measured` | the measured value (a time, a count, a status) |
| `at` | when (ISO 8601, UTC) |
| `evidence` | a link to the run, the screenshot or the record |
| `finding` | the f-… id when it fails (as findings.json has today) |

Example: `{"check": "LOAD", "item": "/directory/", "who": "guest", "target": "2.5 s, 99.5% of the time", "result": "no check", "measured": null, "at": null, "evidence": null, "finding": null}`

## Build order (a spec note)

1. **The register** (this file), its IDs referenced by every gauge criterion.

4. **The gauges read the register**, with **Run checks now** in each gauge's drawer.
